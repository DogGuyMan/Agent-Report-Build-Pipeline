# Confidence and Sourcing

확신도와 출처를 *명시적으로 라벨링*하는 가볍고 범용적인 규율이다. 핵심 가치: **거짓 확신은 신뢰를 무너뜨리고, 확신도를 표시하는 것은 신뢰를 쌓는다.**

## 1. Three-tier confidence labels

주장·추천·추정을 할 때는 어느 티어에 해당하는지 표시한다:

- **Confident** (확신) — 표준/검증된 사실이거나 인용 가능한 출처가 있는 것. 단정적으로 서술해도 된다.
- **Fairly confident** (꽤 확신) — 영향력 있는 통념이지만 도메인/버전/시대에 따라 달라질 수 있다. "보통 ~", "일반적으로 ~" 식으로 표현한다.
- **Uncertain / flag it** (불확실/표시) — 기억에 의존하거나 미검증 상태. "~라고 생각하지만 검증이 필요하다"처럼 명시적으로 서술한다. 절대 단정하지 않는다.

일정/공수 추정처럼 본질적으로 불확실한 것은 **추정치로 못 박고**, 전제와 이를 바꿀 수 있는 요인들을 함께 적는다.

## 1.5 Confidence-to-action binding for design proposals

설계 제안/추천에서는 확신도 라벨만으로 충분하지 않다 — 각 티어는 행동을 BINDS(결속)한다.

- **Confident (🔵 anchor ≥90)** (확신) (인용 가능한 코드/문서): 단정적으로 제안해도 되지만 — 반드시 file:line 또는 문서 인용을 인라인으로 첨부해야 하며, **이번 세션에서** 실제로 읽거나 grep한 것이어야 한다.
- **Fairly confident (🟡 60–89)** (꽤 확신): 옵션 표로 제안한다 — 최소 2개 옵션 + 트레이드오프 + 추천. 근거가 통념 수준이라 단일 지시("X를 구현하세요")로 내리면 검증되지 않은 선택을 사용자 대신 확정하게 되기 때문이다.
- **Uncertain (💭 <60)** (불확실): 제안을 보류한다 — 먼저 도구를 최소 한 번 실행(코드베이스 grep/read, 의존성-소유권 그래프, 또는 레퍼런스 벤치마크 — `benchmark-research-method` 참고)한 뒤 티어를 재산정한다.

측정이나 인용 없이 판단어("~라고 생각한다 / ~에 충실해 보인다")만으로 구성된 추천은 스스로를 **"reference-unverified recommendation"**(레퍼런스 미확인 추천)이라고 라벨링해야 한다. 이번 세션에서 읽지 않은 코드베이스 사실은 티어와 무관하게 **"⚠ not re-verified this session"**(이 세션 미재검증) 태그를 단다 — 과거 대화의 기억은 출처가 아니다.

앵커는 티어 + 정수로 적는다(예: `🔵 92`, `🟡 70`). 티어는 증거 유형(이번 세션에서 읽은 인용 / 통념 / 미검증)으로 결정된다 — 숫자는 결정들 사이를 한눈에 비교하기 위한 앵커 내부의 뉘앙스일 뿐이며, 높은 숫자가 부족한 증거를 대신하거나 티어에 결속된 행동을 면제해주는 일은 절대 없다.

**정수는 확률이 아니다.** 성공확률도 정답확률도 아니고, 결과와 대조해 보정한 적이 없는 자기보고다. 정수는 티어 구간을 넘지 않는다 — 🔵 90–100 · 🟡 60–89 · 💭 0–59. 구간 밖의 숫자가 떠오르면 숫자를 고치지 말고 증거 유형으로 티어를 다시 정한다.

## 2. Objective / 💭 subjective separation

- **Objective**: 인용 가능한 사실(출처, 파일, 라인, 문서 페이지).
- **💭 Subjective**: 가치 판단, 추천, 또는 선호. **주관 표지로 쓰는 💭 에는 숫자를 붙이지 않는다**(`💭 판단`). 숫자가 붙은 💭 는 §1.5 의 불확실 티어(0–59)다 — `💭 80` 은 어느 뜻으로도 성립하지 않는다. 판단에 확신도를 붙이려면 §1.5 의 티어와 구간으로 적는다.

둘을 한 문장에 섞지 않는다. 독자는 *동의해야 할 사실*과 *반박 가능한 의견*을 구분할 수 있어야 한다.

## 3. Cite or retract

사실 주장 각각에 대해: 뒷받침하는 출처가 있으면 인용과 함께 유지하고, 없으면 **철회하거나 "미검증"으로 격하한다.** 그럴듯하지만 근거 없는 주장이 가장 위험한 종류다 — 라이브러리/API/버전 관련 사실은 특히 의심하라, 학습 데이터가 오래됐을 수 있으므로 가능하면 1차 출처(공식 문서)로 검증한다.

## 4. Library/framework facts

라이브러리/SDK/API/CLI 관련 사실을 기억만으로 답하지 않는다. 최신 공식 문서로 먼저 검증한 뒤 답한다. 버전이 지정되어 있으면 그 버전 기준으로 답한다. (문서 조회 도구가 있으면 그것을 우선한다.)

## 5. Machine check — 표기를 쓴 글에 돌린다

표기를 쓴 글(계획 · 결정 로그 · 보고)을 파일로 남겼다면 넘기기 전에 이 스킬의 검사기를 돌린다. 표준 라이브러리만 쓰고, 어느 저장소에서나 이 스킬만으로 돈다. 근거는 평소의 도구(읽기 · 찾기 · 셸)로 모아도 되고 아래의 관찰 세션으로 모아도 된다. 검사기는 다 쓴 글에 한 번 부른다.

```bash
python3 <이 스킬 폴더>/scripts/check_confidence.py <글 파일>… [--root <저장소 뿌리>]
```

| 보는 것 | 수위 |
|---|---|
| 정수가 0–100 안인가 | 밖이면 실패(종료 코드 1) |
| 정수가 티어 구간 안인가 — `💭 80` · `🔵 85` 를 잡는다 | 경고 |
| 숫자나 `실측` 이 붙은 🔵 와 같은 단위(표의 행 · 목록 항목 · 문단)에 근거 인용(`파일:줄` · 링크 · URL)이 있는가 | 경고 |
| 글이 인용한 `파일:줄` 마다 파일이 있고 그 줄이 파일 안인가 | 경고 |

- **통과는 "표기가 계약의 꼴이고 가리킨 줄이 있다" 까지다.** 인용이 주장을 뒷받침하는지, 확신도가 옳은지는 보지 않는다. 통과를 근거로 티어를 올리지 않는다.
- **경고를 없애려고 숫자만 고치지 않는다.** 구간 밖 경고는 증거 유형으로 티어를 다시 정하라는 뜻이고, 인용 경고는 실제로 읽어 인용을 붙이거나 티어를 내리라는 뜻이다.
- 🟡 의 옵션 표와 💭 의 보류는 글에서 기계로 가릴 수 없어 검사기가 보지 않는다 — §1.5 대로 직접 지킨다.
- 다른 저장소의 파일을 인용한 글은 `--root` 로 그 저장소의 뿌리를 준다. `$VAR/…` 로 적은 경로는 변수 값이 없으면 판정하지 않는다.
- 코드 글꼴과 코드 블록 안의 표기는 쓰는 법을 보인 예시로 보고 건너뛴다.

검사기의 시험은 `python3 <이 스킬 폴더>/scripts/test_check_confidence.py` 다. 구간(§1.5)을 바꾸면 검사기의 `BANDS` 도 함께 바꾼다 — 어긋나면 그 시험이 깨진다.

### 관찰 세션 — 읽기 · 찾기 · 실행을 세션에 시킨다

🔵 를 붙일 글의 근거를 모을 때는 평소 도구 대신 관찰 세션으로 읽고 찾고 돌릴 수 있다. 세션은 **무엇을 봤는지**를 대신 기억한다 — 파일별로 본 줄과 그때의 해시, 찾기가 훑은 범위, 돌린 명령과 출력, 부른 횟수. 그래서 다 쓴 글의 인용이 실제로 본 줄인지 대조할 수 있다. 주장 · 전제 · 티어와 정수 · 남은 검색의 어림은 세션에 넣지 않는다 — 쓰는 쪽의 일이다.

한 왕복에 볼 것들은 한 호출에 이어 적는다. 셸의 함수는 호출 사이에 남지 않으므로 호출마다 첫 줄에 다시 적는다.

```bash
o() { python3 <이 스킬 폴더>/scripts/observe.py "$@"; }
o grep 'requireAuth' src/
o read src/auth/middleware.ts 30-60
o run "npm test -- auth"
```

| 명령 | 하는 일 |
|---|---|
| `read <파일> [<줄>\|<줄-줄>]` | 줄 번호와 함께 돌려준다. 이미 본 줄이면 다시 보여 주되 `이미 봄(E3)` 을 붙인다 |
| `grep <정규식> [<경로>…] [-i]` | 맞는 줄을 돌려준다. 0건도 기억한다. 경로가 없으면 git 이 추적하는 파일 전부 |
| `run <명령…>` | 셸로 돌려 출력과 종료 코드를 돌려준다. 셸 문법(`&&` · `\|`)을 쓰면 명령 전체를 따옴표 하나로 묶는다 |
| `show` · `show E7` | 모아 둔 출력을 한꺼번에 받는다 · 그 관찰 하나를 다시 받는다 |
| `check <글 파일>` | 글의 표기와 인용을 보고, 인용한 줄을 이 세션이 봤는지 · 본 뒤 파일이 바뀌지 않았는지를 더 본다 |
| `more <횟수>` | 사용자에게 더 받은 시도 횟수를 더한다 |
| `status` · `end [--out <파일.json>]` | 세션의 상태 · 기억을 남길 자리로 옮기고 세션을 닫는다. `--out` 이 없으면 `<저장소>/.confidence/session-<시각>.json` |

- **세션은 파일이다 — 떠 있는 프로세스가 없다.** 호출마다 Python 이 상태 파일을 읽고, 일을 하고, 다시 쓰고 끝난다. 파일은 처음 관찰할 때 저절로 생기고 저장소 밖 임시 폴더에 있다 — 열어 볼 일이 없다. 6시간 넘게 쓰지 않은 세션은 다음 관찰이 시작될 때 `<저장소>/.confidence/` 로 옮기고 새로 시작한다.
- **출력은 호출마다 고른다.** 그냥 부르면 답에 바로 온다. `--defer` 를 붙이면 확인 한 줄(건수 · 종료 코드 · 줄 수)만 오고 출력은 상태 파일에 쌓인다 — 볼 필요가 생기면 `show` 로 받는다. `run` 은 `--defer` 를 명령 앞에 적는다.
- **시도에는 위가 있다 — 100번.** `read` · `grep` · `run` 을 부를 때마다 한 번이고(실패한 호출도 한 번), 답의 머리에 `[37/100]` 처럼 보인다. 넘기면 세션이 거절한다(종료 코드 3). 그 자리에서 멈추고, 지금까지 본 것과 **남은 검색이 얼마쯤인지**를 사용자에게 보고한다. 더 찾으라는 답을 받은 뒤에만 `more <횟수>` 로 잇는다. 스스로 늘리지 않고, 다른 도구로 돌아가 계속 찾지도 않는다.
- **`run` 은 임의의 셸 명령을 그대로 돌린다.** 이 스크립트를 권한 허용 목록에 넣으면 모든 명령을 허용하는 것과 같다.
- **"봤다" 까지다.** 본 줄이 주장을 뒷받침하는지, 확신도가 옳은지는 세션이 보지 않는다.
- 글을 다 쓴 뒤에는 `o check <글>` 과 `o end --out <글>.evidence.json` 을 한 호출에 이어 적는다. 남긴 JSON 에는 관찰마다 출력까지 들어 있다.

시험은 `python3 <이 스킬 폴더>/scripts/test_observe.py` 다.

## How to apply

추천, 추정, 사실 주장을 할 때마다: ① 어느 확신도 티어인지 라벨링 → ② 객관과 주관을 분리 → ③ 근거 없는 것은 철회한다. 표기를 쓴 글을 파일로 남겼으면 ④ §5 의 검사기를 돌린다(관찰 세션으로 근거를 모았으면 그 세션의 `check`).
