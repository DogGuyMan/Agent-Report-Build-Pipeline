# 코드 지도는 공통 층과 언어 전용 층으로 나누면 통일된다

> ⚠ **정정 (2026-11-05).** 이 보고서의 일부 값은 틀렸다. C++ 원본 메서드는 532 가 아니라 890 이고(8월 지도의 원본은 `full_class_all.json`), 메서드 승격 규모는 C++ 약 5.7배다. "지도를 읽는 모듈 여덟" 도 틀렸다. "대조 측정을 먼저 한다" 는 권고는 철회했다. 맞는 값과 이후 해법은 `public.handoff/2026-11-05-codegraph-verify-unify-resume-handoff.md` 에 있고, 충돌하면 그 문서가 이긴다.

Mode 1 의 `collect-graph` 는 언어마다 다른 수집기를 돌려 `codegraph.json` 하나를 낸다. 이 조사는 세 질문에서 출발했다. 어떤 언어가 와도 코드 그래프를 그리는 도구가 있는가, 언어의 공통 스키마와 배타 스키마를 통일하는 해법이 있는가, UML 이 그 답인가.

결론은 이렇다. **네 언어(C/C++ · C# · Python · TypeScript)를 한 형식으로 내는 도구는 있고, 통일도 가능하다. 다만 호출과 상속까지 한 스키마로 담으면서 네 언어의 정확도가 함께 검증된 도구는 찾지 못했다.** 심볼 · 소속 · 상속 · 호출 · 위치는 공통 층으로 통일되고, 소유 관계 · `friend` · 템플릿 · 데코레이터 · `delegate` 같은 언어 고유 의미는 언어 전용 층에 남겨야 한다.

UML 은 관계 어휘로는 맞지만 저장 스키마나 추출기로는 답이 아니다. 그리고 이번 조사의 가장 큰 발견은 스키마가 아니라 정제 단계에 있었다. C++ · C# 지도에 메서드가 없는 것은 수집기가 못 내서가 아니라 `normalize.py` 가 **이미 수집한 메서드를 버리기 때문**이다.

이 표에서 네 가지가 나온다.

1. **구조는 이미 하나다.** 세 변환 함수(`normalize_cpp` · `normalize_csharp` · `normalize_python`)가 `_assemble`(`src/codewiki/python/machine/normalize.py:470`)로 모여 같은 최상위 칸을 낸다.
2. **멤버 입도 차이의 원인은 정제다.** 🔵 `normalize.py` 에는 `methods` 라는 글자가 한 번도 없다. C++ 메서드는 지도에 들어오지 않고, C# 메서드는 `facts.py --detail` 이 원본을 따로 읽을 때만 쓰인다(`src/codewiki/python/machine/facts.py:328`).
3. **호출 입도 차이의 원인은 수집이다.** 🔵 C++ 원본의 관계 7종에는 호출이 없다. C# 원본의 `depend` 출처 넷(parameter · local · new · return)에도 없다. 호출 정보는 Python 만 갖는다.
4. **소유 관계의 차이는 언어 자체의 차이다.** 🔵 `normalize.py:1264` 는 C# 과 Python 에 언어 차원의 소유 표지가 없어 소유 간선 0 이 정상이라고 적는다.

이 기계에는 `clang-doc` 이 없어 C++ 자유 함수 층도 비어 있다.

🟡 Meta 의 Glean 이 이 문제의 직접적인 선례다. Glean 은 대부분의 언어에 자기 스키마를 두고, 스키마 안에 SQL 뷰와 비슷한 추상 층을 정의해 언어 중립 질의를 제공한다. 공식 글은 이 덕분에 언어별 상세 데이터와 최소공통분모 뷰 사이에서 타협하지 않아도 된다고 설명한다.

🔵 우리 계약도 이미 그 초기 형태다. `codegraph_types.py` 는 C# 갈래의 `origin` · `attrs`, clang-doc 갈래의 `signature` · `doc`, 파이썬 갈래의 `abstraction` 을 `NotRequired` 칸으로 담는다. 슈퍼셋 스키마 방식이 지금 작동하고 있는 셈이다. 외래키 보조 파일 방식에는 선행 조건이 있다. 🔵 1차 노드 id 가 `C%d` 꼴로 실행마다 매기는 번호라(`normalize.py:373` · `:698` · `:1040`) 안정된 열쇠를 먼저 정해야 한다.

## UML 가설의 판정

**맞는 부분.** 의존 · 관계 · 멤버 · 함수를 언어와 무관하게 표현하는 어휘로는 UML 이 유효하다.

- 🔵 `EdgeKind`(`src/codewiki/python/machine/codegraph_types.py:15`) 8종은 이미 UML 어휘다. clang-uml 의 낱말도 이 표로 옮긴다.
- 🟡 Visual Studio 2015 의 UML 표준 프로파일 문서에는 호출을 뜻하는 `«call»` 과 정적 함수 묶음을 뜻하는 `«utility»` 가 있다. 그 원문 판은 OMG 명세에서 다시 확인해야 한다.
- 🟡 코어 위에 프로파일을 얹는 구조가 공통과 배타의 분리와 같다. 같은 문서의 C# 프로파일이 `Is Partial` · `Clr Attributes` 같은 언어 전용 칸을 얹는 실제 사례다.

**부족한 부분.**

- UML 은 표기법과 메타모델이지 추출기가 아니다. 🟡 네 언어를 한 번에 뽑는 UML 추출기는 찾지 못했다. clang-uml 은 C++ 전용이다.
- 🟡 같은 문서는 스테레오타입의 정확한 의미를 현장 규약과 도구가 정한다고 적는다. 표준이 통일하는 범위가 그만큼 좁다.
- 🟡 코드와 UML 의 자동 동기화에는 한계가 있고, 일부 코드 구성 요소만 UML 부분집합으로 자동 추출할 만큼의 의미를 유지한다는 논문이 있다.
- 🔵 · 🟡 조사한 도구 중 UML 을 저장 스키마로 쓰는 것은 없다. SCIP · Joern · code-graph-rag · Glean 은 모두 자체 스키마를 쓴다.

💭 UML 은 간선 어휘로 유지하고, 저장 형식이나 수집 경로로 도입하지 않는다. (확신도 80)

언어 독립을 표방한 메타모델도 살폈다. 🟡 Famix 는 스스로를 여러 언어의 공통분모로 설명하고 언어별 메타모델을 더하는 구조라 방향이 같지만, C# 임포터를 찾지 못했고 임포터 저장소의 규모가 작다. 🟡 KDM 은 언어 독립 표현을 내세우고 Code · Action 패키지를 갖지만, 호출 정의는 원문으로 확인하지 못했고 벤더의 호환 주장이 모호하다는 논의가 있다. 💭 둘 다 설계 참고 자료로만 쓴다. (확신도 70)

|---|---|---|---|
| A. 전면 구체화 | 소비 모듈마다 언어 갈래를 둔다 | 언어 고유 사실을 어디서나 쓴다 | 언어를 더할 때마다 여덟 곳을 고친다 |
| **B. 공통 층 + 언어 전용 층** | 소비자는 공통 층을 읽고, 전용 사실이 필요한 자리만 분기한다 | 언어 추가 비용이 수집과 정제에 갇힌다 | 메서드 승격으로 전수조사 규모가 커지고 계약이 바뀐다 |
| C. 외부 도구로 교체 | `collect-graph` 를 Joern 이나 SCIP 으로 바꾼다 | TypeScript 까지 한 번에 얻는다 | 소유 의미를 잃고, 정확도가 미측정이며, 새 실행 환경이 는다 |

💭 B 를 권고한다. 언어별 구체 대처는 전용 사실을 쓰는 자리에만 적용한다. `facts.py` 가 이미 그 꼴이다. (확신도 80)

💭 C 는 대조 측정 전에는 정하지 않는다. B 의 호출 수집 후보로 먼저 검증하는 것이 위험이 작다. (확신도 75)

## 권고 순서

1. **정제 보강.** C++ · C# 메서드를 노드로 올린다. 수집기는 그대로 두고 `normalize.py` 만 고친다. 💭 멤버 입도 차이를 푸는 가장 싼 길이다. (확신도 85)
2. **호출 수집 대조.** 골든 C++ · C# 저장소에서 Joern 과 SCIP 을 돌려 현재 지도와 노드 · 간선 · 위치를 대조한다. clangd 호출 계층과 Roslyn 확장도 함께 비교한다.
3. **TypeScript 수집기.** 🔵 지금은 `ts` 수집기가 없어(`src/codewiki/python/machine/lang_select.py:37`) `prep` 이 막힌다. 2번 결과로 경로를 고른다.
4. **언어 전용 층의 형식 결정.** `NotRequired` 칸을 유지할지 보조 파일로 뺄지 정한다.
5. **`verify-graph` 재개.** `collect-graph` 와 `schedule-batches` 사이의 검사 단계 설계는 시험까지 쓴 뒤 2026-11-04 에 되돌렸다. 노드 어휘가 위 결정에 달려 있으므로 그 뒤에 다시 본다.

## 비용과 미결정

🔵 전수조사 대상인 1차 노드는 C++ 185개, C# 214개다. 💭 메서드를 전량 올리면 원본 총계 기준으로 C++ 약 3.9배, C# 약 3.5배가 되고, LLM 세션과 비용도 비슷하게 늘 것이다. 원본 총계에는 1차가 아닌 요소가 섞일 수 있어 어림값이다. (확신도 65)

아래는 혼자 정하지 않는다.

- 메서드 승격 범위 — 전량인가, 공개 표면이나 호출이 닿는 것만인가
- 호출 수집 방식 — 언어별 수집기 확장, LSP, SCIP, Joern 중 무엇인가
- 안정된 노드 열쇠의 꼴
- 언어 전용 층의 저장 형식

## 검증 한계

- Joern · SCIP · code-graph-rag 를 실행하지 않았다. 네 언어를 같은 잣대로 잰 정확도 자료도 찾지 못했다.
- `«call»` · `«utility»` 의 근거는 Visual Studio 2015 보관 문서다. OMG UML 원문과 KDM 의 호출 정의는 읽지 못했다.
- TypeScript 서버와 Roslyn 의 LSP 지원은 코드 검색 일치 수만 봤다.
- code-graph-rag 와 Codebase-Memory 의 지원 표는 각 프로젝트의 자기 설명이다. 별 수는 품질을 보증하지 않는다.
- C++ · C# 숫자는 8월 산출물이고, C++ 지도에는 clang-doc 이 합쳐지지 않았다.
