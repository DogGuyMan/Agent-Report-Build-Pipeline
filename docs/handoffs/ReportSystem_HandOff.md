## 0. 목적 — 이것부터 읽어라

**이 시스템의 목적은 AI가 틀리지 않게 막는 것이 아니다.**

> **AI의 판단이 맞는지 틀린지를, 텍스트가 아니라 시각화를 통해 사람이 빠르게 판정하도록 돕는 것.**

사용자는 "AI의 판단이 가끔 틀리는 것은 어쩔 수 없다"고 명시적으로 받아들였다. 목표는 오판을 줄이는 것이 아니라 **오판을 빨리 찾는 것**이다.

| | 예방 (아님) | **판정 지원 (이것)** |
|---|---|---|
| 대상 | 에이전트의 행동 | **사람의 검토** |
| 수단 | 규율 강제 | **시각화** |
| 성공 | 오판이 덜 나온다 | **오판을 빨리 찾는다** |

이 구분이 모든 설계 판단을 가른다. 어떤 기능을 추가할지 망설여지면 **"이게 사람의 판정 시간을 줄이는가"**를 물어라. 에이전트를 더 엄격하게 만드는 방향은 이 시스템의 목적이 아니다.

사용자가 오판을 알아채는 신호는 **"객체지향적 직감"**이며, 사용자는 이 직감의 외재화를 명시적으로 포기했다. 따라서 도구는 판단을 대신할 수 없고, **직감이 발동할 재료를 빨리 눈앞에 놓는 것**까지가 역할이다.

### 권장 순서

```

```

## 1. 왜 이 작업이 생겼나

사용자는 이미 성숙한 스킬 체계를 운영 중이다. 아래는 **이미 해결된 문제**이므로 다시 제안하지 말 것.

- 배치·소유권 오판 → `design-decision-discipline` §6.1이 실제로 잡고 있음
- 확신도 무표기 단정 → `confidence-and-sourcing` §1.5의 티어→행동 결속이 작동 중
- 미확정 설계의 조기 문서화 → 상태 태그가 작동 중
- 자기 제안 무검증 → `code-design-review-lenses`의 Self-review gate 존재

**남은 실패는 하나다: 규율을 전부 지켰는데도 추상화 시점 판단이 틀린다.** 즉 과잉 설계.

단, §0을 다시 보라 — 이 실패를 **막는 것**이 목표가 아니다. 이 실패는 어쩔 수 없는 것으로 받아들이고, **사람이 그것을 빨리 알아보게** 만드는 것이 목표다. 아래 세 기전은 "왜 사람이 알아보기 어려운가"의 설명이지, 차단해야 할 대상 목록이 아니다.

그 기전이 세 곳에서 확인됐다.

**(a) 인용이 대안 검토를 면제한다.** `confidence-and-sourcing` §1.5에서 🔵(인용 있음)는 옵션표 의무가 없고 🟡만 있다. 그런데 현재 실패 유형은 "인용은 정확한데 결론이 틀린" 것이다. 오판이 정확히 🔵 경로로 빠져나간다. 근거가 튼튼할수록 대안을 안 보게 되는 구조다.

**(b) `expected`는 grep이 안 된다.** `design-decision-discipline` §2.5는 "implementer count now/expected — from grep, not estimation"을 요구하지만 `expected`는 원리적으로 grep 불가다. 과잉 설계의 정당화는 전부 그 절반에 실려 있고, 그 절반은 아무도 검사하지 않는다.

**(c) 승격 게이트가 눈멀었다.** `architecture-design-workflow`의 승격 조건(build / visual check / golden test)을 과잉 설계는 전부 통과한다. 추상화가 부족하면 아프지만 과잉이면 안 아프기 때문이다.

# Track A — D축 도입

## A-1. 확정된 결정 (사용자 확정, 변경 금지)

| ID | 결정 |
|---|---|
| D-1 | 확신도를 **E축(증거 확신도)**과 **D축(결정 불확실성)** 2축으로 분리 |
| D-2 | 옵션표 의무를 E축이 아니라 **D축**에 결속 |
| D-3 | D축 지표는 **3종 고정** (아래) |
| D-4 | 승격을 3상태로. 구조 신설 결정은 N커밋 경과 후 D1 재측정 |
| D-5 | **도구는 판정하지 않는다.** D축 계산·정렬·병치만 하고 결론은 내지 않음 |

### 두 축의 역할

| | E축 (증거 확신도) | D축 (결정 불확실성) |
|---|---|---|
| 묻는 것 | 내가 읽은 게 확실한가 (as-is) | 결론이 유일한가 (to-be) |
| 표기 | 🔵 / 🟡 / 💭 (기존 그대로) | 신설 |
| 결속되는 행동 | 인용 첨부 / 도구 실행 | **옵션표 / 정렬 우선순위** |

이 분리로 `🔵 92 + D 높음` = **"근거는 확실하나 대안 검토는 필수"**가 표현 가능해진다. 현재 체계에서 표현 불가능한 상태이고, 그 불가능성이 정확히 누수 지점이었다.

E축의 기존 규정(🔵는 이번 세션 인용 필수, 💭는 도구 실행 후 재산정)은 **전부 그대로 유지**한다.

### D축 계산 (D-3)

세 지표 모두 사람 판단 없이 계산된다. 이것이 D-5를 가능하게 하는 조건이다.

| 지표 | 계산 | 점수 |
|---|---|---|
| **D1 구현자·소비자 수** | grep, **now만** (expected 무시) | 둘 다 ≥2 → 0 / 하나만 → 1 / 둘 다 ≤1 → 2 |
| **D2 expected 출처** | `expected` 주장에 file:line 또는 계획문서 D# 인용이 붙었는가 | 인용 있음 또는 주장 없음 → 0 / 없음 → 2 |
| **D3 트리거 명시** | "지금 채택 / X가 올 때 채택" 문장이 있는가 (§4 YAGNI) | 있음 → 0 / 없음 → 1 |

**D 총점 0–5**

| D | 색 | 결속되는 행동 |
|---|---|---|
| 0–1 | 초록 | 단일안 제안 가능 |
| 2–3 | 노랑 | **옵션표 필수** (최소 2안 + 트레이드오프) |
| 4–5 | 빨강 | 옵션표 필수 + **"먼저 볼 것" 블록에 노출** |

**⚠ 이전 버전에 있던 "D 4–5 → 제안 보류"는 폐기됐다.** 그것은 에이전트가 판단을 대신하는 게이트였고, §0의 목적(사람이 판정)과 어긋난다. 제안은 전부 나오고, D축은 **어디부터 볼지를 정하는 신호**로만 쓴다.

옵션표 의무는 남는다. 다만 근거가 바뀐다 — 예방이 아니라 **판정 재료 제공**이다. 옵션표가 있으면 사용자가 "AI는 A를 골랐는데 B가 나아 보인다"를 즉시 판단하고, 없으면 후보를 스스로 세워봐야 한다. **판정 시간을 줄이는 쪽은 오히려 옵션표다.**

### 두 축의 시각 표현이 겹치지 않게 할 것

E축(🔵/🟡/💭)과 D축이 둘 다 3색이라, 배지를 나란히 붙이면 혼동된다. **형태를 다르게 한다.**

| 축 | 표현 |
|---|---|
| E축 | 기존 그대로 — 이모지 + 정수 배지 (`conf-badge`) |
| D축 | **결정 행의 좌측 테두리 색** — 배지 아님 |

### 정렬이 서사를 깨지 않게 할 것

geometry 문서의 D0~D8은 논리 순서로 배열돼 있다(D0가 전제, D2가 본질). **D 내림차순으로 뒤섞으면 그 흐름이 무너진다.**

- **본문 결정 표: 원래 순서 유지.** 좌측 테두리 색으로만 D축 표시.
- **보고서 맨 위에 "먼저 볼 것" 블록을 따로 둔다.** 거기에만 D 상위 3개를 뽑는다.

사용자는 앞서 "보고서 맨 위에 무엇이 와야 하나"에 **"되돌리기 어려운 결정"**이라고 답했다. 되돌리기 비용은 D축 지표에서 빠졌으므로, 지금은 D 상위로 채우고 그 지표가 나중에 들어오면 합친다.

### 지연 승격 (D-4)

핵심 논리: **오늘 셀 수 없는 것을 N커밋 뒤에는 셀 수 있다.** 지연 승격은 `expected`(예측)를 `now`(측정)로 바꾸는 장치다.

```
[제안됨] ──[빌드/시각/골든 통과]──> [잠정됨] ──[N커밋 후 D1 재측정]──> [검증됨 <커밋>]
                                                      │
                                                      └─[수가 안 늘었다]──> 제거 후보 표시
```

- **구조 신설** 결정만 `[잠정됨]`을 거친다. 그 외는 기존 2상태.
- 재검토 시점에 **D1만 다시 grep**한다.
- 제거를 강제하지 않는다. **표시만 하고 판단은 사람.**

### 상태 태그 — 한국어로 통일

실제 문서가 한국어를 쓰고 있고 `architecture-design-workflow`도 이를 동등하게 인정하므로 한국어가 정본이다. `proposed/accepted` 영어 표기는 쓰지 않는다.

`[잠정됨]`은 세 번째 상태의 **제안 이름**이며 사용자 확정 전이다.

### 결정 로그 표 형식 — 4컬럼이 정본

실제 spec 2건이 `| # | 결정 | 상태 | 신뢰도 |` 4컬럼으로 일관되게 쓰고 있다. `architecture-design-workflow` 템플릿의 6컬럼(`ID/Decision/Chosen/Rationale/Status/Confidence`)은 실사용 흔적이 없다.

**문서가 스킬을 이긴 사례다. 스킬 템플릿을 4컬럼으로 고쳐라.** D축 컬럼을 더해 5컬럼이 된다. 근거 서술은 표 셀이 아니라 본문 절(geometry 문서의 §3.1~3.4 방식)에 둔다.

## A-2. Task A1 — 소급 검증 (여기서 시작)

**목적:** D축 3지표가 과잉 설계를 실제로 예측하는지 확인. 예측력이 없으면 D-2~D-5는 폐기 대상이다.

### 절차

1. 과거 spec / plan / 결정 기록에서 **구조 신설 결정**(새 인터페이스·모듈·레이어·클래스)만 추출한다.
2. 그중 **사후에 번복·제거·통합된 것**을 식별한다. `git log`의 삭제된 타입, 결정 로그의 번복 기록, 보고서의 `⚠ 번복 기록` 블록을 근거로 삼는다.
3. 각 결정에 D1/D2/D3를 **수동 채점**한다. 이 단계는 스크립트를 쓰지 않는다.
4. 결과를 2×2로 교차한다.

| | 나중에 제거됨 | 살아남음 |
|---|---|---|
| D 높음 (4–5) | (참양성) | (거짓양성) |
| D 낮음 (0–1) | **(거짓음성 — 치명적)** | (참음성) |

### ⚠ 구현 함정 — D1은 "그때의 grep"이다

D1(구현자·소비자 수)은 **결정 시점의 수**여야 한다.

`grep`은 코드에서 특정 문자열이 몇 군데 나오는지 세는 것이다(예: `: public ITechnique`를 검색해 구현자 수를 셈). "결정 시점"은 그 결정을 내리던 날의 코드 상태를 말한다.

지금 grep하면 그 이후 추가된 것까지 세어 결과가 오염된다. 2026-07-27 결정을 오늘 세면 한 달치가 섞인다. `git show <결정_커밋>:<파일경로>`로 그날 스냅샷을 꺼내 세거나, `git log -S`로 도입 시점을 특정할 것.

**이 함정을 놓치면 소급 검증 전체가 무효다.**

### 완료 조건

- 표본 수를 명시한다. 몇 개인지 모르면 완료가 아니다.
- **거짓음성(D 낮은데 제거됨) 사례를 개별 서술한다.** 지표가 놓친 부분이고 정보량이 가장 많다.
- 표본이 적어 통계적 유의성이 없다는 것을 명시한다. **"검증됨"이라고 쓰지 말 것.** 목표는 "명백한 반례가 없는가" 수준의 sanity check이다.
- D2/D3 중 예측에 기여하지 않은 지표가 있으면 지목한다.

**Task A1이 끝나기 전에 D축 관련 코드를 쓰지 말 것.**

# Track B — 보고서 렌더러

## B-1. 지금 상태와 결함

현재 대시보드는 **매번 LLM이 손으로 쓰는 단일 HTML 88~93KB**다. 외부 스크립트 0개, `<style>` 인라인, Graphviz SVG를 본문에 붙여넣음.

**실측된 결함 — 다이어그램 글자가 2.5px다.**

```
.page      max-width 1120px, padding 36px  →  내용 폭 1048px
.diagram-grid  1fr 1fr, gap 16px           →  패널당 516px
.svg-wrap  padding 14px + 테두리           →  실제 SVG 폭 486px

원본 SVG    1961pt = 2615px
축소율      486 / 2615 = 18.6%
노드 글꼴   10pt ≈ 13.3px  →  화면상 2.5px
```

`.svg-wrap`에 `overflow-x: auto`가 있지만 `svg { max-width: 100% }`가 무력화해서, 넘치는 대신 줄어든다. **읽을 수 없는 상태다. 브라우저로 열어 육안 확인 후 착수할 것.**

**CSS 6,599자가 두 파일에서 바이트 단위로 동일하다(diff 0줄).** 추출 가능한 안정 레이어가 실측으로 확인됐다.

### 왜 Vite가 아닌가

vite-plugin-singlefile은 **클라이언트 JS 번들을 만든 뒤 그것을 인라인**하는 도구다. 결과물에 런타임이 들어가는 것을 전제한다. 우리 요구("클라이언트 런타임 0")와 정면 충돌한다.

우리 CSS는 이미 6.6KB 고정 문자열이고 SVG도 정적이다. Node에서 파일 읽어 `<style>`로 감싸 끼워넣으면 끝이라, 번들러의 CSS 파이프라인조차 불필요하다.

### 산출물 불변식

**빌드된 `report.html`에 `<script>` 태그가 pan/zoom 하나 말고 더 있으면 잘못된 것이다.**

`grep -c '<script' out/report.html` 로 기계가 검사한다. 사람 판단이 필요 없다.

### React가 결과물에 안 들어간다

`renderToStaticMarkup`은 빌드 시점 Node에서 HTML 문자열만 만든다. 산출물은 순수 HTML+CSS다. React는 빌드 시점에만 존재한다.

- **`data.ts`에는 결정만.** 나머지는 전부 `report.tsx`.

### slug

파일명에 쓰는 짧은 식별자다. `2026-07-27-geometry-winding-ownership-design.md`에서 `geometry-winding-ownership` 부분. `architecture-design-workflow`의 `specs/YYYY-MM-DD-<topic>-design.md`의 `<topic>` 자리와 같다.

### `report init <slug>` 동작

- **해당 slug의 작업 파일이 이미 있으면** → 기존 것을 그대로 이어서 쓴다(rev.2 방식). 새로 만들지 않는다. `builderVersion`이 현재와 다르면 경고한다.
- **없으면** → 빈 스켈레톤을 만든다. 필수 구조는 있고 내용만 비어 있다.

### builder 버전 관리

- `~/report-builder`는 git 저장소. **컴포넌트 API가 바뀌는 갱신마다 태그**(`v1`, `v2`).
- `data.ts`에 `builderVersion: "v2"` 한 줄.
- `report build`가 현재 버전과 비교 → **불일치면 경고만.** 빌드는 시도한다.
- 진짜 옛 버전이 필요하면 `git worktree add /tmp/rb-v2 v2` 후 거기서 빌드. (`using-git-worktrees` 스킬이 이 용도다.)

**함께 지킬 규율: 컴포넌트는 추가만 한다.** props 제거·의미 변경 금지. 새 props를 추가하는 쪽으로만 가면 대부분의 갱신에서 과거 보고서가 그냥 빌드된다. 버전 고정은 이 규율이 깨진 드문 경우의 안전망이다.

## B-5. Graphviz SVG 인라인 규칙

- **`dot -Tsvg_inline`을 쓴다** (Graphviz 10.0.1+). `<?xml?>` 선언과 DOCTYPE 없이 나와 HTML 본문 삽입에 맞다. 버전이 낮으면 헤더를 수동 제거.
- **`width`/`height` 속성을 제거하고 `viewBox`만 남긴다.** 컨테이너 div로 감싸 반응형.
- **id에 접두사를 붙인다.** 한 페이지에 SVG가 2개 이상이면 `graph0`, clipPath/marker id가 충돌해 렌더가 깨진다. 빌드 후처리로 치환.
- 다크 모드가 필요해지면 `fill="black"` → `fill="var(--fg)"` 치환. **인라인 SVG여야 CSS 변수를 상속한다.**

## 4. 함정

**거울 함정.** 과잉 설계를 잡는 도구를 만들면서 그 도구를 과잉 설계하는 것. `d-axis.mjs`는 지표 3개를 계산하는 스크립트다. 플러그인 구조, 지표 레지스트리, 추상 인터페이스가 나오면 그 자체가 이 작업이 잡으려는 실패다. **§2.5를 이 스크립트 자신에게 적용하라 — 구현자 1, 소비자 1이면 인터페이스를 만들지 마라.**

**지표 증식 유혹.** D-3은 3종 고정이다. 소급 검증 중 "이것도 넣으면 좋겠다"가 반드시 생기는데, 넣지 말고 **기록만 하고 사용자에게 보고**하라. 지표를 늘리면 검증 기준이 흔들려 검증 자체가 무의미해진다.

**컴포넌트 즉석 리팩터링.** §B-4 참조. 보고만 하고 사후 일괄.

**조기 성공 선언.** 표본이 5~10개일 것이고 그 정도로는 아무것도 증명되지 않는다. `verification-before-completion` 스킬을 적용하고 근거 없이 "작동한다"고 쓰지 말 것.

**A1 건너뛰기.** 설계가 이미 상세해서 바로 구현하고 싶어질 것이다. D축이 예측력이 없으면 A2~A4가 전부 폐기된다.

## 5. 작업 규약

- 사용자의 기존 스킬을 **전부 준수**한다. 특히 `confidence-and-sourcing` §1.5, `code-design-review-lenses`의 Self-review gate.
- 구조 제안 시 `design-decision-discipline` §2.5의 4항목 공개, §2.7의 축 선언.
- 확신도는 🔵/🟡/💭 + 정수. 🔵는 **이번 세션에서 읽은** file:line만 인정.
- 결정은 `[제안됨]`으로 먼저 기록하고 검증 후 승격.
- 객관 사실과 💭 주관 판단을 한 문장에 섞지 않는다.
- 사용자는 **구현물보다 의사결정용 보고서를 먼저** 받기를 선호한다. A1의 산출물은 코드가 아니라 문서다.
- 설명은 메커니즘 우선(원리 → API 세부), 한국어 + 영문 기술용어 병기.
- **약어와 압축 표현을 피할 것.** 이 문서 초안이 그 이유로 한 번 반려됐다.
