## 0. 목적과 한계

정적 분석 도구가 코드를 **정확히·빠짐없이 색인하도록** 돕는 코딩 규칙이다. 도구를 바꾸지 않고도 분석 품질을 올리는 것이 목적이다.

### ⚠ 한계 — 이걸 먼저 읽어라

**이 규약은 자기 코드에만 적용된다.**

Track C의 본 목적은 **"남의 코드베이스를 빠르게 이해"**하는 것이고, 남의 코드에 규약을 강제할 방법은 없다. 따라서:

| 용도 | 쓸 수 있는 것 |
|---|---|
| **내 프로젝트** | 컨벤션 + 도구 |
| **남의 코드베이스** | **도구만** |

**이 규약이 도구 조사를 대체하지 않는다.** 자기 코드에서 문제 하나를 지워 파일럿을 단순하게 만들 뿐이고, 도구는 여전히 필요하다.

## 1. 헤더 자기충족 — 최우선

### 문제

`src/fsm`은 헤더 두 개(`fsm_state.h`, `state_machine.h`)뿐이고 `.cpp`가 없다. 🔵 clang-uml 노드 **0건**으로 나왔다 — 모듈 하나가 보고서에서 통째로 사라졌다.

원인은 libclang이 **번역 단위(translation unit, TU)** 단위로 AST를 만들기 때문이다. `compile_commands.json`에는 `.cpp`만 들어가고, `.h`는 어떤 `.cpp`가 include할 때만 딸려 들어온다. 그 헤더에 도달하는 TU가 하나도 없으면 존재하지 않는 것과 같다.

**가장 나쁜 점: 사라졌다는 사실조차 안 보인다.** 0건은 에러가 아니라 정상 종료다.

### 규칙

**모든 헤더는 자기 자신만 include해도 컴파일되어야 하고, 그것을 검증하는 번역 단위가 존재해야 한다.**

최소 형태 — 모듈마다 더미 `.cpp` 하나:

```cpp
// src/fsm/fsm.cpp
#include "fsm_state.h"
#include "state_machine.h"
```

권장 형태 — 자기충족성 테스트(self-containment test) 자동 생성:

```cmake
# 헤더 목록을 순회하며 #include "<헤더>" 한 줄짜리 .cpp를 생성하고
# 하나의 타겟으로 묶어 컴파일한다
file(GLOB_RECURSE HDRS CONFIGURE_DEPENDS src/*.h)
foreach(h ${HDRS})
  # generated/selfcontain_<name>.cpp 생성 → 타겟에 추가
endforeach()
```

### 얻는 것 둘

1. **모든 헤더에 TU가 생겨 색인 누락이 원천적으로 사라진다** ← 우리 목적
2. 헤더가 자기 의존을 전부 include하는지 컴파일로 검증된다 ← 이 관례의 원래 목적

두 번째가 원래 목적이고 첫 번째가 부수효과인데, 이 프로젝트에서는 부수효과가 본체다.

### 효과

**거의 완전.** 이 규칙 하나로 문제 2(헤더 전용 모듈)가 자기 코드에서 사라지고, **도구를 바꿀 필요가 없어진다.**

## 2. 외부 의존 격리

### 문제

🔵 clang-uml 클래스 노드 203개 중 **101개(49.8%)가 외부**였다 — GLFW, GLM, Assimp 등.

- 다이어그램에 그리면 절반이 남의 코드 → 노드 폭발의 직접 원인
- 사실 테이블에 넣으면 프롬프트 예산의 절반이 낭비
- 그리고 읽는 사람이 알 필요가 없다

### 이미 되어 있는 것

**네임스페이스 규율이 서 있다.** 🔵 `file:line` 정답 10건이 전부 `SJH::`로 시작한다. `src/` · `extern/` 물리 분리도 되어 있다. 덕분에 필터가 한 줄로 끝난다.

```yaml
include:
  namespaces: [SJH]
exclude:
  paths: [vcpkg_installed, extern]
```

### 추가 규칙

**헤더에서는 forward declaration, 구현(.cpp)에서 include.**

```cpp
// renderer.h
namespace SJH { class Mesh; }        // forward declaration
class Renderer { Mesh* mMesh; };     // 포인터/참조면 이걸로 충분

// renderer.cpp
#include "mesh.h"                    // 실제 사용은 여기서
```

원래 컴파일 시간 때문에 하는 관례인데, **외부 타입이 헤더 파싱 단계에 안 들어와서 그래프도 같이 깨끗해진다.** PIMPL은 같은 원리의 더 강한 형태다.

### 효과

**상당.** 이미 반쯤 적용돼 있어 남은 이득은 forward declaration 정도다.

## 3. 검색 가능한 이름

### 문제

역방향 질의("누가 이 심볼을 부르나")를 할 도구가 없어 **grep으로 떨어진다.** 그리고 C++에서 grep은 오버로드 해소·매크로 전개·템플릿 실체화·ADL·`using` 별칭을 못 본다.

🔵 실제 실패 사례: 수집 세션이 `src/fsm`을 `std::function`·함수포인터·`Callback`으로 grep해서 **"해당 없음"**이라 판정했다. 실제 기제는 `uint64_t` 비트마스크였다. grep 키워드에 없었으니 안 나왔고, 안 나왔으니 없다고 결론냈다.

> **grep은 찾은 것은 믿을 수 있지만 못 찾은 것은 믿을 수 없다.**

### 규칙 넷

**3-1. 매크로로 호출을 감싸지 않는다.**

```cpp
#define RENDER_CALL(x) x->Draw()    // 금지 — grep이 호출을 통째로 못 봄
```

**3-2. `using namespace` 금지. 타입 별칭은 최소로.**
같은 타입이 여러 이름으로 나타나면 grep이 한 이름만 찾는다.

**3-3. 오버로드 대신 이름을 분리한다.**

```cpp
// 이전
void Draw();
void Draw(int index);
void Draw(Mesh& mesh);

// 이후
void DrawAll();
void DrawIndexed(int index);
void DrawMesh(Mesh& mesh);
```

오버로드는 C++의 정당한 기능이지만 **검색 가능성 관점에서는 비용이다.** `Draw`를 grep하면 세 함수가 섞여 나오고 어느 것인지 구분되지 않는다.

**3-4. 이름을 고유하게 짓는다.**

`Init()` · `Update()` · `Get()`은 코드베이스에 수백 개다. `InitGLContext()`면 grep이 유효해진다. **이름 하나가 함수 하나에 대응할수록 grep이 정확해진다.**

### 한계 — 컨벤션으로 못 푸는 것

```cpp
IDrawable* obj = ...;
obj->Draw();          // 실제로 어느 구현이 불리나?
```

**가상 호출은 실행 시점에 정해진다. 정적 도구도 못 푼다** — 모든 구현을 후보로 낼 뿐이다. 콜백·함수 포인터로 넘긴 호출도 같다.

### 효과

**부분.** grep의 신뢰도를 올릴 뿐 도구를 대체하지 못한다. 역방향 질의 도구는 여전히 필요하다.

## 4. 하지 말 것

### 4-1. 중첩 타입을 평평하게 펴지 말 것

🔵 clang-uml은 `Program::UniformBlock`을 `Program##UniformBlock`으로 낸다. 구분자가 `::`가 아니고 바깥 클래스가 `namespace` 필드에 안 들어간다.

`ProgramUniformBlock`으로 펴면 이 문제가 사라진다. **하지만 하지 말 것.**

중첩 타입은 스코프를 좁히는 정당한 설계다. `UniformBlock`이 `Program` 밖에서 의미가 없다면 안에 두는 것이 맞다. **도구 출력 형식 때문에 코드 설계를 바꾸는 것은 방향이 반대다.**

`normalize.py`에서 `##` → `::` 치환하고 앞부분을 namespace에 합치면 끝이다. 다섯 줄이다.

> 단, 도구마다 규약이 다르다. **후보를 바꾸면 치환 규칙을 다시 만들어야 하므로, 비교표에 "중첩 타입 표기 방식"을 반드시 적을 것.**

### 4-2. 외부 타입을 래핑하지 말 것

`glm::vec3`를 자기 타입 `Vec3`로 감싸면 그래프가 깨끗해진다. **하지만 그래프를 위해 래퍼를 만드는 것은 과잉이고, 유지보수 비용이 이득보다 크다.** 필터 설정으로 충분하다.

### 4-3. 색인을 위해 설계를 바꾸지 말 것 (일반 규칙)

4-1과 4-2를 관통하는 원칙이다. **코드 설계는 코드의 목적을 위해 정해지고, 도구는 거기에 맞춰야 한다.** 예외는 §1(헤더 자기충족)뿐인데, 그것은 색인 목적이 아니라 **원래 좋은 관례**라서 예외다.

## 6. 도구 조사에 미치는 영향

이 규약을 적용해도 **도구 조사는 그대로 필요하다.** 본 목적이 남의 코드베이스이기 때문이다.

| | 자기 코드 (파일럿) | 남의 코드 (본 목적) |
|---|---|---|
| 문제 1 역방향 질의 | 도구 필요 (컨벤션은 보조) | **도구 필요** |
| 문제 2 헤더 전용 | **컨벤션으로 해결** | **도구 필요** |

즉 **파일럿은 문제 1만 남지만 본 목적은 둘 다 남는다.** 조사는 넓게 가야 하고, 두 문제가 서로 반대 방향(1번=libclang 계열, 2번=텍스트 계열)을 가리키므로 조합안까지 봐야 한다.

## 7. 기존 규약과의 관계

이 프로젝트에는 이미 크로스플랫폼 코딩 규약이 있다 — `windows.h`는 `#ifdef _WIN32` 안에서만, `WIN32_LEAN_AND_MEAN` + `NOMINMAX`, 고정 크기 정수 타입, `long` 금지, 슬래시 통일 경로, 바이너리 모드 I/O.

**이 문서는 그 규약의 확장이지 대체가 아니다.** 같은 자리에 절을 하나 더 만들어 합치는 것이 관리상 낫다.

한 가지 상호작용이 있다. `#ifdef __APPLE__` / `#ifdef _WIN32` 분기는 **플랫폼마다 색인 결과를 다르게 만든다** — clang-uml은 전처리 후를 보므로 macOS에서 뽑은 그래프에 Windows 전용 클래스가 없다. 이건 컨벤션으로 없앨 문제가 아니라 **`codegraph.json`의 `platform` 필드로 다루는 문제**다 (Track C §6 함정 3).
