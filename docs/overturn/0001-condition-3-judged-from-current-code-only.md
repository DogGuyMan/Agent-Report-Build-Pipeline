# 0001 · 지금 코드만 보고 "런타임 교체 시나리오가 없다" 고 판정했다

| | |
|---|---|
| 날짜 | 2026-09-08 |
| 자리 | 러너 공통 단계 기계 설계, 축 1 |
| 뒤집은 이 | 사용자 |
| 상태 | 확정 |

## 무엇을 주장했나

세 실행기의 공통축으로 상속 기반 State 패턴을 만드는 것이 `design-decision-discipline` §2 의
**조건 ③(런타임 교체 시나리오가 실제로 존재한다)** 을 만족하지 못한다고 판정했다. 근거로 든 것:

> 세 실행기의 단계 순서는 편집 시점에 고정된 목록이고, 전이는 전부 "실패 아니면 다음 칸" 이다.
> 분기하는 사람이 없는 그래프가 된다.

그리고 상속 없는 데이터 주도 드라이버를 권고했다.

## 무엇으로 뒤집혔나

사용자가 동기를 밝혔다.

> 추후 파이프라인 개발 후 **확장에 열려있고 변경에 닫혀있는 구조**를 원했기 때문이다.
> Mode 1 에서 항상 고정적으로 흘러가는 게 아니라 손쉬운 **Fall-Back 착지점**,
> **Cascade 분기 착지점**을 교체할 수 있을 것이라 보았다.

교체 시나리오는 존재했다. 코드에 아직 없었을 뿐이다.

## 왜 틀렸나 — 판단의 어느 단계에서 갈렸나

**측정 자체는 맞았다.** 지금 세 루프의 실패가 전부 `break` 한 갈래로 흡수된다는 것은 사실이고,
지금도 사실이다. 틀린 것은 **그 측정으로 조건 ③을 판정할 수 있다고 본 것**이다.

§2 의 조건 셋은 성격이 다르다.

| 조건 | 무엇을 묻나 | 무엇으로 답하나 |
|---|---|---|
| ① 공통 추상 인터페이스가 뜻이 있는가 | 지금 코드의 모양 | grep |
| ② 부르는 쪽이 기반 포인터로 부르는가 | 지금 코드의 모양 | grep |
| ③ **런타임 교체 시나리오가 실제로 있는가** | **이 구조로 무엇을 하려 하는가** | **물어보기** |

①②는 저장소가 답한다. ③은 저장소가 답하지 못한다 — 아직 안 쓴 코드에 대한 질문이기 때문이다.
grep 으로 ③을 판정하면 **언제나 "없다" 가 나온다.** 이미 있으면 리팩터링할 일도 없었을 테니까.

## 패턴 — 다음에 쓸 검사

**구조 제안을 기각하기 전에, 그 구조를 원하는 사람에게 동기를 한 번 묻는다.**
특히 "그것을 만들면 앞으로 무엇을 하기 쉬워지길 바라는가" 를 묻는다.

기각의 근거가 아래 꼴이면 멈추고 물어본다.

- "지금 코드에 그런 사례가 없다"
- "아직 한 번도 그렇게 쓰인 적이 없다"
- "소비자가 하나뿐이다"

셋 다 **현재 시제**다. 그리고 셋 다 리팩터링 직전에는 거의 항상 참이다.

**반대로, 기각이 정당한 꼴은 이렇다** — 미래를 물어본 뒤에도 답이 안 나오는 경우다.

- 물어봤는데 "그냥 그게 좋아 보여서" 라는 답이 온다
- 물어봤는데 나온 시나리오가 §1 의 **편집 시점 변경**이다 (다음에 코드를 고칠 때 달라진다)

이 기록이 뒤집은 것은 §2 의 내용이 아니라 **§2 를 적용하는 순서**다.
