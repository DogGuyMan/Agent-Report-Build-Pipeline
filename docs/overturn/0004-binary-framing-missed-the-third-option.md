# 0004 · 두 제약이 충돌한다고 보고 하나를 포기했다 — 둘을 다 만족하는 셋째 안이 있었다

| | |
|---|---|
| 날짜 | 2026-09-11 |
| 자리 | 러너 단계 기계 설계, D14 (두 번째 번복) |
| 뒤집은 이 | 사용자 |
| 상태 | 확정 |

## 무엇을 주장했나

2026-09-10 세션이 D14 를 이렇게 뒤집었다.

> 앞선 판은 갈래 C(계획 파일에 `only_files` 를 싣는다)를 골랐다. 사용자가 갈래 D(경고만)로 바꿨다.
> 결정적 사유는 **소유 경계**다 — C 는 `machine/survey_plan.py` 의 `SurveyPlan` TypedDict 를
> 고쳐야 하는데, 이 문서의 "범위 밖"이 못박아 두었다.

그리고 D 의 대가로 셋(⑴⑵⑶)을 "경고로는 안 막힌다" 며 **개선 대상 M1-1** 로 남겼다.
즉 "범위를 파일에 남긴다(검출 가능)" 와 "`machine/` 을 안 건드린다(소유 경계)" 를 **양립 불가**로 보고
후자를 택했다.

## 무엇으로 뒤집혔나

사용자가 셋째 안을 냈다.

> 옛 판과 새 판이 JSON 으로 산출될 수 있는 파일이라면 diff.json 또한 만들 수 있을 것이다.
> 그건 기계적인 작업이고… Diff 작업을 기계적으로 만드는 파이프라인을 한 번 두기만 하면 된다.

`warmup` 이 **러너 소유** 파일 `warmup-diff.json` 을 쓴다. 담는 형은 `machine/warmup.py` 가
**이미 선언한** `Verdicts` 다. `machine/` 은 한 줄도 안 바뀌고, M1-1 의 ⑴⑵⑶ 은 전부 닫힌다.

## 왜 틀렸나 — 판단의 어느 단계에서 갈렸나

두 제약을 **같은 파일에 대한 요구**로 읽었다.

| 제약 | 실제로 요구하는 것 | 09-10 세션이 읽은 것 |
|---|---|---|
| 검출 가능 | 범위가 **어딘가 파일에** 남아 있을 것 | `survey-plan.json` **안에** 있을 것 |
| 소유 경계 | `machine/` 의 TypedDict 를 **안 고칠** 것 | 그러니 파일에 못 싣는다 |

첫 제약을 "그 파일 안에" 로 좁혀 읽는 순간 둘은 충돌한다. "어딘가 파일에" 로 읽으면 충돌하지 않는다 —
새 파일을 하나 두면 된다. **제약을 한쪽 안의 어휘로 옮겨 적었기 때문에** 셋째 안이 안 보였다.

두 안(C · D)이 이미 표에 올라 있었다는 것도 거들었다. 표에 둘이 있으면 "둘 중 하나" 로 읽힌다.
표는 옵션의 **전수**가 아니라 **지금까지 떠오른 것**인데, 그 차이를 잊었다.

## 패턴 — 다음에 쓸 검사

**두 제약이 충돌한다고 결론내기 전에, 각 제약을 어느 안의 어휘도 쓰지 않고 다시 적는다.**

    제약 A 를 안 X 의 이름 없이 한 문장으로:  ______
    제약 B 를 안 Y 의 이름 없이 한 문장으로:  ______
    두 문장이 정말 서로를 배제하는가?  아니면 X · Y 가 우연히 둘 다 한쪽만 만족한 것인가?

이번 경우 — A = "범위가 파일에 남는다", B = "`machine/` 을 안 고친다". 둘은 배제하지 않는다.
30초면 나왔을 질문이다.

**특히 위험한 꼴 — "대가" 표를 쓰면서 그 대가를 M1-1 처럼 "개선 대상" 으로 넘길 때.**
대가가 셋이나 남는데 그것을 후속으로 미루고 있다면, 그것은 절충이 아니라 **선택지가 모자란 신호**다.
후속 항목을 적기 전에 셋째 안을 한 번 찾아본다.
