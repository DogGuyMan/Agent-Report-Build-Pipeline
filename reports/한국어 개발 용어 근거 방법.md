# 이미 짝지어진 자원이 한국어 표기 근거를 넓힌다

영어 개발 용어의 한국어 표기를 추론 없이 근거하려면, 영어와 한국어의 대응(정렬, alignment)이 자원 안에 **이미 들어 있어야 한다.** 이 조건을 만족하는 원천은 세 갈래뿐이다. 첫째는 번역 단위(translation unit)가 영어와 한국어를 한 레코드에 묶는 현지화 번역 메모리(translation memory)이고, 둘째는 저자가 문장 안에서 직접 짝을 지은 괄호 병기, 셋째는 문서끼리 언어 간 링크(interlanguage link)로 이어진 지식 기반(knowledge base)이다. 이번 조사에서 실측으로 확인한 가장 큰 추가 원천은 세 가지다. **Mozilla Pontoon 한국어 TMX(번역 단위 110,374개, MPL-2.0, 33 MB, 커밋 고정)**, React·Vue·Rust·TypeScript 공식 문서 한국어판 저장소(괄호 병기 **2,938건**, 대부분 CC BY 4.0·MIT·Apache-2.0), 그리고 기각된 한국어 변형까지 정규식으로 담은 ko.react.dev 용어집(68항목)이다. 통계 정렬기·비교 말뭉치·음차 판별·형태소 분석은 근거 행을 만들지 못하고 보조 열(column)만 만든다. 웹·코드 말뭉치는 규모는 크지만 정렬이 없어서 괄호 패턴을 세는 데만 쓸 수 있다. 기계 번역(machine translation)과 대형 언어 모델(large language model) 문헌은 용어집을 '주어진 것'으로 소비할 뿐 근거를 만들지 않고, 주요 제공자 셋은 **온도 0 에서도 출력이 결정적이지 않다**고 문서에 밝힌다. 다만 그 문헌의 용어 일관성 지표(terminology consistency)는 참조 번역 없이 결정적으로 돌아가므로 ko-dev-terms 의 측정 열로 옮겨 올 수 있다. 가장 큰 공백은 개념·공학 어휘다. `postcondition` 과 `single source of truth` 는 Mozilla TMX 와 문서 저장소 7곳 어디에도 사실상 없었다. 이 공백을 메울 후보(위키백과·Wikidata·우리말샘·온용어·TTA)는 공교롭게도 이번 세션 네트워크가 막은 곳들이어서, 수록량을 하나도 재지 못했다.

## 근거 표지와 한눈에 보는 판정

이 보고서는 근거의 출처를 세 표지로 가른다. **🔵 실측**은 이번 세션에 원천을 직접 받아 센 값이다. 조사 노트에 커밋과 명령이 함께 기록되어 있다. 그중 Mozilla TMX 의 번역 단위 수와 예시 용어 탐침 결과, ko.react.dev 용어집 항목 수, Hangulize 규칙 목록은 이 보고서를 쓰는 중에 다시 받아 같은 값을 얻었다(아래 "재실측"). **🟡 요약**은 원문 페이지가 막혀서 검색 결과 스니펫(snippet)에만 기댄 것이다. **💭 추론**은 위 둘에서 도출한 판단이고, 붙은 정수는 확신도다.

## 번역 메모리와 문서 번역판, 두 원천이 실측 근거를 가장 크게 늘린다

괄호 병기 채굴(parenthetical translation mining)은 학계에서 오래된 기법이다. Lin 외(2008)는 중국어·일본어·한국어 웹 문서가 용어 뒤 괄호에 영어를 다는 관행을 단어 정렬로 채굴했다. 중국어 웹에서만 **2,600만 쌍 이상**을 뽑았다 🟡 ([ACL Anthology P08-1113](https://aclanthology.org/P08-1113/); [초록 사본](https://sciweavers.org/node/207110)). 후속 연구가 꼽은 핵심 난제는 둘이다. 하나는 괄호 앞 원어 구간의 **왼쪽 경계(left boundary)** 이고, 다른 하나는 괄호가 번역이 아닌 경우(모델 번호·약어·부연)를 걸러 내는 일이다 🟡 ([N09-1048](https://preview.aclanthology.org/fix_video/N09-1048.pdf)). 한국어 신문에서는 괄호가 모델 번호에도 쓰여 추출 오류가 많았다는 보고가 있다 🟡 ([Jung 외 2006](https://www.rcs.cic.ipn.mx/2006_18/Clustering%20of%20English-Korean%20Translation%20Word%20Pairs%20Using%20Bi-grams.pdf)). 한국어 전용 선행 연구인 이·서(2002)는 기본 대역 사전, 음운 유사도, 부분 일치를 묶어 경계를 정했다 🟡 ([KoreaScience](https://koreascience.or.kr/article/JAKO200211921122601.page)). 이번에 문서 저장소에서 센 괄호 병기에서도 경계 문제가 그대로 나왔다. "할 불변성 (invariant)" 처럼 앞말이 딸려 오는 사례가 있었다 🔵. ko-dev-terms 는 영어 쪽이 입력으로 고정되므로 이 문제를 결정적으로 바꿔 풀 수 있다. 괄호 앞 1어절·2어절·…·k어절 구간을 각각 별도 후보 행으로 내면, 경계를 '고르는' 문제가 '열거하는' 문제로 바뀌어 판정하지 않는다는 설계와 맞는다 💭 70.

### Mozilla 한국어 번역 메모리는 도구 어휘를 덮고 개념 어휘에서 비어 있다

`mozilla-l10n/mt-training-data` 저장소의 `ko/ko_pontoon.tmx` 는 Pontoon 이 만든 TMX 한 파일이다. 커밋 `cda8e0c` 기준 33,486,005 바이트, **번역 단위 110,374개**이고 저장소 라이선스는 MPL-2.0 이다 🔵 재실측 ([ko_pontoon.tmx](https://github.com/mozilla-l10n/mt-training-data/blob/cda8e0c/ko/ko_pontoon.tmx)). 영어 쪽을 단어 경계 정규식으로 탐침하면 결과가 뚜렷하게 갈린다. `breakpoint` 100건, `callback` 12건, `edge` 122건이 나왔고, **`side effect` · `single source of truth` · `postcondition` 은 모두 0건**이었다 🔵 재실측. `breakpoint` 100건의 한국어 쪽 가운데 98건에 `중단점` 이 들어 있었다. 다만 (영어, 한국어) 쌍의 중복을 없애면 **75쌍**으로 줄어든다 🔵 재실측. firefox · firefox-beta · firefox-os 가 같은 문자열을 되풀이하기 때문이다. 쌍 단위로 중복을 지우지 않으면 개수가 약 3분의 1 부풀려진다는 뜻이다. `edge` 는 다의어 위험을 보여 준다. 대부분이 화면 기하(`오른쪽 가장자리`)였고, 첫 일치는 "Amazon edge" → "우위" 였다. 그래프 의미의 `간선` 근거로는 셀 수 없다 🔵. 번역 단위마다 붙은 `tuid` 에 프로젝트와 파일 경로가 들어 있으므로(`firefox:devtools/client/debugger.properties` 등), 증거 행에 이 값을 같이 실으면 사람이 맥락을 판단할 수 있다. `devtools` 같은 경로 접두어로 거르면 결정적으로 정밀도를 올릴 수 있다 💭 70. 이 메모리가 UI 어휘에 강하고 개념 어휘에 빈 이유는, 현지화 번역 메모리가 '사용자 화면에 보이는 문자열'만 담기 때문으로 보인다 💭 75.

같은 계열의 커밋 고정 원천은 더 있다. `firefox-l10n` 의 `ko/` 에는 FTL 메시지 약 12,532행과 properties 항목 약 4,049개가 있고, `ko/devtools/` 에 `whypaused-breakpoint = 중단점에서 일시 중지됨` 같은 개발 도구 문자열이 있다 🔵 ([firefox-l10n/ko](https://github.com/mozilla-l10n/firefox-l10n/tree/3b935d8/ko)). OPUS 메타데이터 저장소의 `statistics.yaml` 을 보면 en-ko 규모가 KDE4 v2 TMX 69,609 단위, GNOME v1 XML 정렬 565,920개, PHP 매뉴얼 v1 TMX 10,909 단위다. 다만 **GNOME 의 TMX 판은 165 단위뿐**이어서 받는 형식에 따라 양이 크게 다르다. 셋 다 2018 년 스냅숏이고 라이선스는 "원 출처와 같음" 이다 🔵 메타데이터 ([OPUS KDE4 v2](https://github.com/Helsinki-NLP/OPUS/tree/42d4fbe/corpus/KDE4/v2); [GNOME v1](https://github.com/Helsinki-NLP/OPUS/tree/42d4fbe/corpus/GNOME/v1); [PHP v1](https://github.com/Helsinki-NLP/OPUS/tree/42d4fbe/corpus/PHP/v1)). 실제 TMX 파일은 `object.pouta.csc.fi` 가 막혀 받지 못했다. 다른 UI 원천은 손이 더 간다. Visual Studio Code 한국어 언어 팩(`microsoft/vscode-loc`, MIT)은 한국어 문자열이 약 28,000개지만 **영어 원문이 저장소에 없어서** 소스의 `nls.localize` 호출과 결합해야 한다 🔵 ([vscode-loc](https://github.com/microsoft/vscode-loc/tree/62d5443/i18n/vscode-language-pack-ko)). Chromium `.xtb` 는 메시지 지문(fingerprint) ID 로만 식별되어 `.grd` 원문과 맞춰야 한다 🔵 ([generated_resources_ko.xtb](https://github.com/chromium/chromium/blob/4f6e0f57/chrome/app/resources/generated_resources_ko.xtb)). GTK `po/ko.po` 는 `msgid` 1,811개(LGPL) 🔵 ([GNOME/gtk](https://github.com/GNOME/gtk/blob/2f51d3c/po/ko.po)), AOSP `values-ko` 는 문자열 2,402개(Apache-2.0)인데 미러의 마지막 커밋이 2025-03 이다 🔵 ([AOSP 미러](https://github.com/aosp-mirror/platform_frameworks_base/blob/1cdfff55/core/res/res/values-ko/strings.xml)). 쓸 수 없는 원천도 둘 확인했다. Apple 현지화 용어집은 개발자 로그인 뒤 DMG 로만 배포되고 재배포가 막혀 있는 것으로 보인다 🟡 ([gist](https://gist.github.com/douglashill/c5b08a9099883475294d27cecc56ec29)). Microsoft Learn 한국어 문서 저장소(`MicrosoftDocs/azure-docs.ko-kr` 등)는 2026-10-28 익명 `git ls-remote` 에서 자격 증명을 요구했다. 2020 년에는 공개였던 현지화 저장소가 지금은 닫힌 것이다 🔵 ([Wayback 2020-12](https://webcf.waybackmachine.org/web/20201206060401/https://github.com/MicrosoftDocs)).

### 문서 번역 저장소는 프로젝트마다 다른 '사용'을 보여 준다

7개 저장소를 커밋 고정으로 받아 `.md`/`.mdx` 계열만 센 결과, **"한글(English)" 괄호 병기가 2,938건** 나왔다 🔵. 저장소별로는 ko.react.dev 160, Vue docs-ko 813, doc.rust-kr 448, ko.javascript.info 750, typescript-kr 594, TypeScript-Website-Localizations 91, progit2-ko 82 다 ([ko.react.dev](https://github.com/reactjs/ko.react.dev/tree/89f79e9e971e9ad424ea5ebabdf8d5fa66c87375); [docs-ko](https://github.com/vuejs-translations/docs-ko/tree/6e646acb5687510feda533281faa546b26ea243c); [doc.rust-kr](https://github.com/rust-kr/doc.rust-kr.org/tree/cbbea2ca830cb0c090651111b3a18f5d5beabace); [ko.javascript.info](https://github.com/javascript-tutorial/ko.javascript.info/tree/2489814d15d09791bf6edfe00774ce0171e3bd1e); [TypeScript-Website-Localizations](https://github.com/microsoft/TypeScript-Website-Localizations/tree/40b00e0a2434315e760cff02d0739533e7ff0e8e)). 같은 `side effect` 도 프로젝트마다 우세한 표기가 다르다.

이 표는 '승자를 고르지 않고 근거만 나열한다'는 계획의 설계가 실제 데이터와 맞는다는 직접 증거다 🔵. 다른 예시 용어는 거의 비어 있다. `edge` 의 그래프 의미인 `간선` 은 7곳 모두 0 이었고, `엣지`·`에지` 는 대부분 "에지 케이스(edge case)" 맥락이었다. `single source of truth` 는 Vue 의 "진실의 원천" 3회뿐이었고, **`postcondition` 은 `사후 조건` · `후조건` · `(postcondition)` 모두 7곳 전부에서 0** 이었다 🔵. 해석할 때 주의할 점이 셋 있다. 첫째, 각 저장소는 자기 용어집으로 표기를 강제한다(ko.react.dev 는 textlint 로 검사한다). 그래서 저장소 안의 빈도는 독립 표본이 아니라 **편집 정책의 결과**다. 저장소를 합산하지 말고 저장소 단위로 묶어 보여야 큰 저장소 하나가 전체를 지배하지 않는다 💭 80. 둘째, ko.javascript.info 는 "basically CC-BY-NC, revocable and exclusive" 이고 progit2-ko 는 CC BY-NC-SA 3.0 이라 상업 배포에 걸린다 🔵. 셋째, angular-ko(2017)와 typescript-kr(2021)은 갱신이 멈췄다 🔵 ([angular-ko](https://github.com/angular/angular-ko/tree/6048a5b39a3afb57047f847f37c986e4c8275616)).

### 기계가 읽을 수 있는 커뮤니티 용어집은 사실상 하나다

ko.react.dev 의 `textlint/data/rules/translateGlossary.js` 는 **`target:` 항목 68개**를 담은 JS 모듈이다 🔵 재실측. 항목 꼴은 `{sources: [/\bComponent\b/, /컴퍼넌트/, /컴포넌츠/], target: '컴포넌트', meta: {term, discussions: [2], note}}` 이다. 영어 정규식과 함께 **피해야 할 한국어 변형의 정규식**, 그리고 논의한 이슈 번호가 들어 있다. 위키의 용어집 표는 이 파일에서 자동 생성되며, 라이선스는 CC BY 4.0 이다 🔵 ([ko.react.dev](https://github.com/reactjs/ko.react.dev/tree/89f79e9e971e9ad424ea5ebabdf8d5fa66c87375)). 나머지는 기계 판독성이 떨어진다. Vue docs-ko 의 `glossary` 는 개념 설명이지 대역표가 아니다. angular-ko 의 `ko-trans-guide.md` 는 글머리표 목록이고, progit2-ko 는 초판을 따른다는 지침만 둔다. rust-kr 는 용어 논의를 git 밖 이슈에 둔다 🔵. GNOME 한국어 팀 용어집은 위치(`wiki.gnome.org/KoreanTranslation`)만 확인했고 🟡 ([l10n.gnome.org/teams/ko](https://l10n.gnome.org/teams/ko)), 한빛·인사이트·제이펍 같은 IT 출판사의 대역표는 공개 자료를 찾지 못했다. 정리하면, 용어집 항목은 **한 팀의 결정(정책 근거)** 이고 같은 저장소 본문의 빈도는 **그 결정이 강제된 결과(사용 근거)** 다. 둘을 같은 종류의 행으로 세면 이중 계산이 된다 💭 75.

## 지식 기반과 국가 자원은 공식 후보를 주지만 사용 빈도는 주지 않는다

지식 기반 갈래에서 라이선스와 스냅숏이 모두 깔끔한 것은 Wikidata 와 위키백과 SQL 덤프다. Wikidata 의 구조화 데이터는 **CC0** 이고 매주 JSON 덤프로 나온다 🟡 ([Wikidata:Data access](https://www.wikidata.org/wiki/Wikidata:Data_access)). 렉심(Lexeme) 엔티티에는 label·alias 가 없으므로 영어→한국어 조회는 일반 항목의 `ko` label·alias 로 해야 한다 🟡 ([WikibaseLexeme JSON](https://doc.wikimedia.org/WikibaseLexeme/master/php/md_docs_2topics_2json.html)). SPARQL 서비스(WDQS)는 데이터가 살아 있어 시점을 고정할 수 없고, 60초 제한시간이 있으며, 2025-05 에 그래프가 둘로 나뉘었다. 그래서 재현 가능한 경로는 덤프뿐이다 🟡 ([WDQS 분할](https://meta.wikimedia.org/wiki/WikiCite/WDQS_graph_split); [CEUR-WS](https://ceur-ws.org/Vol-4064/PD-paper3.pdf)). 위키백과 쪽 방법론은 Erdmann 외(2008)가 정립했다. 언어 간 링크만 쓰면 문서당 최대 1개라 범위가 좁지만, **넘겨주기(redirect)와 링크 앵커 텍스트를 더하면 크게 나아지고 병렬 말뭉치 방식보다 낫다**고 보고했다 🟡 ([Erdmann 외, DASFAA 2008](https://aminer.org/pub/53e9b484b7602d9703f8b48d/an-approach-for-extracting-bilingual-terminology-from-wikipedia)). 이 방식의 두 전제는 "언어 간 링크로 이어진 제목은 서로의 번역이다" 와 "넘겨주기 제목은 대상 제목의 동의어다" 이다 🟡 ([Ivanova, BUCC 2012](https://aclanthology.org/www.mt-archive.info/BUCC-2012-Ivanova.pdf)). 실패 양상도 분명하다. `side effect` 처럼 의학 항목과 컴퓨터 과학 항목이 따로 있는 동음이의 용어에서는, "(computer science)" 접미사나 상위 개념 경로처럼 미리 정한 규칙으로 항목을 골라야 결정성이 유지된다 💭 80. 또 위키백과 표제는 백과사전 문체라서 현장의 음차형(`사이드 이펙트`)은 넘겨주기에만 있거나 아예 없을 수 있다 💭 65. 다국어 지식 그래프의 꼬리 엔티티(tail entity)는 일본어·중국어 이름 범위가 15% 미만이라는 보고가 있지만 한국어 수치는 없다 🟡 ([arXiv 2311.15781](https://arxiv.org/pdf/2311.15781)). **예시 4개 용어의 실제 한국어 label·넘겨주기는 접속 차단으로 하나도 확인하지 못했다.** Wiktionary 는 wiktextract 가 번역 칸을 JSONL 로 뽑아 주지만 데이터 라이선스 문구는 확인하지 못했다 🟡 ([wiktextract](https://github.com/tatuylonen/wiktextract)). BabelNet 은 자체 비상업 라이선스이고 최신판은 일괄 덤프 없이 API 로만 쓴다는 보고가 있어, 로컬 고정이라는 전제와 맞지 않는다 🟡 ([BabelNet license](https://babelnet.org/full-license); [사용자 글](https://groups.google.com/g/conceptnet-users/c/Pegrq0JGEWA)).

국립국어원 계열에서 **통째로 로컬에 받을 수 있다고 확인된 것은 우리말샘뿐**이다. 로그인한 뒤 "사전 내려받기 → 전체 내려받기" 로 XML ZIP 을 받는다는 설명이 있고, 공개 API 에는 일괄 내려받기가 없다 🟡 ([mukenko/opendict-db](https://github.com/mukenko/opendict-db)). 라이선스는 CC BY-SA 2.0 KR 이다 🟡 ([data.go.kr 우리말샘](https://www.data.go.kr/data/15019347/openapi.do)). 2016 년 개통 브리핑은 "저작권이 설정되지 않는다" 고 적어 지금 안내와 어긋나는데, 오래된 자료다 🟡 ([korea.kr](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156157539)). 표제어는 2022-02 기준 1,137,315개이고, 전문 분야를 67개로 나눈다 🟡 ([탐라문화 2022](http://jst.re.kr/upload/pdf/RC00095177.pdf)). 정보는 "참여자 제안 정보" 와 "전문가 감수 정보" 두 층위로 표시된다 🟡 ([bartoc.org](https://bartoc.org/en/node/20607)). "정보·통신" 분야의 표제어 수와 원어 칸 채움률은 찾지 못했다. 동일조건(share-alike) 조항 때문에 우리말샘에서 뽑은 행을 공개하면 파생 데이터도 CC BY-SA 로 내야 할 가능성이 있다. 이는 법적 판단이라 여기서 결론 내지 않는다 💭.

**온용어**는 계획의 TTA 결정과 직접 닿는다. 2025-05-15 에 정식 개통한 국립국어원 용어 플랫폼으로, 36개 기관의 용어집 53종에서 **용어 120만 개**를 통합했다 🟡 ([뉴시스 2025-05-15](https://www.newsis.com/view/NISX20250515_0003177165)). 출처 목록에 **"정보 통신 용어 사전 (한국정보통신기술협회)"** 가 있다는 스니펫이 있다 🟡 ([온용어](https://kli.korean.go.kr/term)). 사실이라면 "TTA 는 손 조회만" 이라는 지금의 결정을 다시 볼 근거가 된다. 그러나 온용어는 인증키가 필요한 온라인 API 이고(`start` 최대 1000) 🟡 ([온용어 Open API](https://kli.korean.go.kr/term/bbs/indexOpenApiInfo.do)), 항목마다 공공누리 1유형·2유형(상업 이용 금지)·CC BY-SA 가 섞여 있으며 🟡 ([항목 2175842](https://kli.korean.go.kr/term/trgtWord/indexTrgtWord.do?trgtWordNo=2175842)), 일괄 내려받기는 확인되지 않았다. TTA 정보통신용어사전 자체는 2026-10-28 재확인에서도 **공식 Open API·공공데이터·일괄 내보내기를 찾지 못했다.** 기계 경로라고는 비공식 Ruby 스크래퍼 gem 뿐이다 🟡 ([tta_terms_api](https://www.rubydoc.info/gems/tta_terms_api/0.0.2)). 항목 URL 에는 `word_seq` 식별자가 있어 손 조회 기록의 고정에는 쓸 수 있다 🟡 ([TTA 항목 예](http://terms.tta.or.kr/dictionary/dictionaryView.do?word_seq=177559-1)). TTA 는 분과위원회 검토와 심의위원회 상정을 거쳐 **"표준용어"** 를 결정한다 🟡 ([TTA 정보통신용어표준화위원회](https://committee.tta.or.kr/standard/general.jsp?commit_code=WORDSTD); [공지 35](http://word.tta.or.kr/noticeView.do?public_no=35)).

나머지 국가·표준 자원은 범위가 좁거나 막혀 있다. 다듬은 말은 약 18,3xx건의 "다듬을 말 → 다듬은 말" 쌍과 순화 이력을 가진다 🟡 ([다듬은 말 목록](https://www.korean.go.kr/front/imprv/refineList.do)). 외래어 표기 용례 API 는 응답에 **관련 표기(이표기·오표기)** 필드를 준다. 한국어 공식 자원 가운데 비권장 표기를 기계적으로 돌려주는 거의 유일한 필드로 보이지만 개발 용어 수록은 작을 것이다 🟡 ([kornorms Open API](https://korean.go.kr/kornorms/main/openAPI.do)), 💭 60. 대한수학회 수학용어 사전은 영문명–한글명 목록을 HTML 로 노출하지만 이용 조건은 확인하지 못했다 🟡 ([KMS 목록](https://www.kms.or.kr/mathdict/list.html?alpa=&key=&keyword=&sort=ename&start=420)). 그래프 이론의 vertex·edge 는 교과·수학회·실무가 서로 다른 표기(꼭짓점·정점·노드 / 간선·모서리·엣지)를 쓰는 대표 영역이다. 한국정보과학회(KIISE) 용어집은 존재조차 확인하지 못했다. 정보기술 용어 표준은 "KS X ISO/IEC 2382" 가 아니라 **KS X 0001 시리즈**로 제3자 목록에 보이고 유료 문서로 추정된다 🟡 ([KS X 0001-1](https://ndls.org.cn/standard/detail/d6c6c7e9c0fb2d2ebd28edcf06ba080c)). ISO/IEC 2382 는 2015 년판이 현행이다 🟡 ([ISO proj 63598](https://iss.rs/sr_Latn/project/show/iso:proj:63598)). IEC Electropedia 에는 한국어 용어 **20,766개**가 2017~2018 년에 등재됐다 🟡 ([전기학회논문지 2019](https://koreascience.kr/article/JAKO201925454183556.pdf)). 그러나 전기전자 어휘이고, 데이터베이스의 상당 부분을 복제하려면 상업 계약이 필요하다 🟡 ([IEC copyright](https://webstore.iec.ch/en/copyright)). 정보통신 분야의 국가 고시 전문용어 목록은 찾지 못했다. 가장 가까운 것은 2022 년 한국지능정보사회진흥원이 정보통신기술 용어 약 500개에서 순화어 50개를 고른 사업이다 🟡 ([뉴시스 2022-11-24](https://www.newsis.com/view/NISX20221124_0002099356)).

### 상태 필드는 TBX 가 운반하고 한국 자원은 부분적으로만 대응한다

국제 용어 관리 표준은 용어마다 우선(preferred)·허용(admitted)·비권장(deprecated)·대체됨(superseded) 상태를 달 수 있게 한다. TBX 는 이를 `administrativeStatus`(예 `deprecatedTerm-admn-sts`)나 `normativeAuthorization` 에 싣는다 🟡 ([DIN 데이터 범주](https://din.de/en/services/din-term/datenkategorien); [JATS term-status](https://jats.nlm.nih.gov/publishing/tag-library/1.3/attribute/term-status.html); [translate5](https://jira.translate5.net/browse/TRANSLATE-3434)). EU 용어집 IATE 는 이 사용 권고 표지와 **별도로** 1~4 별의 신뢰도(reliability)를 둔다 🟡 ([IATE 도움말](https://online-help.iate.europa.eu/?p=5325)). 계획이 쓰는 Microsoft TBX 는 Hugging Face 로더가 정의·품사·용어만 읽어서 상태 필드가 보이지 않는다. 다만 로더가 읽지 않았을 뿐 파일에는 있을 수 있다 🟡 ([ms_terms.py](https://huggingface.co/datasets/microsoft/ms_terms/blob/refs%2Fpr%2F2/ms_terms.py)). 한국 자원의 표지(다듬을 말·오표기·전문가 감수·표준용어)는 TBX 값과 1:1 로 대응하지 않는다. 특히 우리말샘의 감수 층위는 IATE 신뢰도와 같은 축(근거의 신뢰도)이지 사용 권고 축이 아니다. 그러니 원천의 원문 값을 그대로 옮기고, 두 축을 한 칸에 섞지 않는 편이 안전하다 💭 75.

### 공식 대체어가 있다는 것과 쓰인다는 것은 다른 사실이다

용어 정착 연구는 계획이 권위 출처(①)와 사용 빈도(②)를 나눈 것을 지지한다. Kim(2023, *International Journal of Corpus Linguistics*)은 국립국어원이 성공 사례로 내세운 한국어–영어 낱말 쌍 18개를 두 말뭉치·6년 범위로 조사했다. 결과는 **한국어 대체어 보급이 영어 사용을 줄이지 못했고, 영어 기반 낱말이 대체어와 함께 늘었다**는 것이다 🟡 ([EBSCO 초록](https://www.ebsco.com/articles/language-and-linguistics/b65c5723-0e17-54f1-8718-a78554bb7a92/a-corpus-based-study-of-anglicized-neologisms-in-korea-a-diachronic-approach-to-korean-and-english-word-pairs)). 2017~2021 년 신어 1,856개 중 58.2% 가 차용 요소를 담았다 🟡 ([*Lexicography* 2023 초록](https://www.ebsco.com/articles/language-and-linguistics/cf8d6c95-3be3-5eb0-b781-8240ec0823a2/korean-neologisms-of-2017-2021-correlation-between-borrowing-semantic-characteristics-and-lexicographic-representation)). 문금현(2024)은 순화어의 정착 조건으로 의미 범위의 정확한 대응, 음절 수가 늘지 않을 것, 결합 환경이 같을 것을 들었다. 응답자들은 이미 굳은 외래어는 받아들여야 한다고 답했다 🟡 ([KCI](https://www.kci.go.kr/kciportal/landing/article.kci?arti_id=ART003054456)). 정착도는 지금까지 인지율·이해율·사용률 설문, 표준국어대사전 등재 여부, 포털 뉴스 검색 빈도로 쟀다 🟡 ([박용찬 2005](https://www.korean.go.kr/nkview/nklife/2005_1/2005_0103.pdf)). 셋 다 재현 가능한 스냅숏이 없다. 고정된 커밋에서 정렬된 병기를 세는 ko-dev-terms 방식이 재현성에서는 이 문헌들보다 앞선다 💭 70. **정보통신·소프트웨어 용어만 따로 말뭉치로 잰 정착률 연구는 찾지 못했다.**

## 웹·코드 말뭉치는 크지만 정렬이 없어 괄호 패턴으로만 쓸 수 있다

계획은 검색 엔진 적중 수(hit count)를 이미 배제했다. 학계 근거도 같다. Kilgarriff(2007)는 적중 수가 방법이 공개되지 않은 추정치라서 언어학 증거로 쓰는 것은 비과학적이라고 했다 🟡 ([J07-1010](https://preview.aclanthology.org/menus/J07-1010/)). 2차 인용에 따르면 같은 질의를 다음 날 다시 돌리자 30건 중 6건이 두 배 넘게 달랐다 🟡 ([Sketch Engine 블로그](https://www.sketchengine.eu/?p=5597)). 재현 가능한 대안은 날짜가 고정된 Common Crawl 파생 말뭉치다. 한국어 규모는 CC-100 이 **56억 토큰·54.2 GiB**(2018 년 스냅숏) 🟡 ([XLM-R 논문](https://arxiv.org/pdf/1911.02116)), mC4 가 약 260억 토큰 🟡 ([mT5 논문](https://arxiv.org/pdf/2010.11934)), OSCAR 23.01 이 38~46 GB(접근하려면 약관 동의 필요, 크기 표기 불일치) 🟡 ([OSCAR 문서](https://oscar-project.github.io/documentation/versions/oscar-2301)), **FineWeb-2 `kor_Hang` 이 5,816만 문서·94.73 GB(ODC-By)** 다 🟡 ([FineWeb-2 카드](https://huggingface.co/datasets/HuggingFaceFW/fineweb-2/blob/cab26bb3cab1ca7c26bb13a48f80fc3d2def4620/README.md)). 이 가운데 라이선스가 가장 분명한 것은 FineWeb-2 다. Google Books Ngram 에는 한국어가 없다 🟡 ([Ngram 언어 목록 사본](https://static.hlt.bme.hu/semantics/external/pages/n-gram/en.wikipedia.org/wiki/Google_Ngram_Viewer.html)). 국립국어원 모두의 말뭉치는 이용 약정 원문을 확인하지 못했고, 2022 년 문어 말뭉치 저작권 분쟁으로 서비스가 중단된 적이 있다 🟡 ([Korpora README](https://github.com/ko-nlp/korpora); [비즈한국](https://bizhankook.com/articles/woongjin-loses-ai-copyright-lawsuit.html)).

이 말뭉치들의 근본 한계는 크기가 아니라 **정렬이 없다는 점**이다. 웹에서 `부작용` 을 센 수는 그것이 `side effect` 의 번역으로 쓰인 것인지 의학 용어인지 말하지 못한다. 결정적으로 정렬을 얻는 유일한 방법은 웹 말뭉치 안에서도 "한글(English)" 괄호 패턴을 세는 것이다. 이렇게 하면 계획의 ② 갈래를 일반 웹으로 넓히는 셈이 된다. 대신 일반 웹에서는 개발 텍스트가 작은 부분이라 "일반 독자에게 익숙한 표기" 쪽으로 기운다. 94.73 GB 를 매번 훑을 수는 없으므로, 한 번 추출해 후보 빈도표만 남기는 방식이 현실적이다 💭 70. 개발 블로그(velog·Tistory)와 OKKY 같은 한국어 개발 Q&A 는 고정 가능한 공개 데이터셋을 찾지 못했다. GitHub 공개 이벤트를 담은 GH Archive 는 BigQuery 비용이 들고 이벤트 데이터의 권리가 불분명하다 🟡 ([gharchive.org](https://gharchive.org/)).

코드 말뭉치는 오프라인 전제와 맞지 않는다. The Stack v2 는 접근 제한(gated)이 걸려 있고, 일괄 내려받으려면 Software Heritage·INRIA 와 약정해야 한다 🟡 ([the-stack-v2](https://huggingface.co/datasets/bigcode/the-stack-v2)). 2026-07 에 나온 The Stack v3 는 학습 분할만 **약 15.9 TB** 이고, 데이터셋은 ODC-BY 이지만 파일마다 원 라이선스가 남는다. 거부(opt-out)한 저장소는 패치 릴리스마다 빠지므로 릴리스마다 값이 달라진다 🟡 ([stack-v3-train](https://huggingface.co/datasets/HuggingFaceCode/stack-v3-train/blob/main/README.md)). GitHub 코드 검색 API 는 인증이 필요하고 분당 9회로 제한되며 결과가 1,000건에서 잘린다. 살아 있는 색인이라 적중 수와 같은 재현 불가 문제를 그대로 가진다 🟡 ([GitHub Docs](https://docs.github.com/en/rest/search/search); [API 한도](https://fulll.github.io/github-code-search/reference/github-api-limits.html)). 공개 코드의 한국어 주석 비율을 잰 수치는 찾지 못했다. 식별자는 대개 영어이므로 한국어 근거는 주석과 독스트링(docstring)에 몰릴 것으로 추정된다 💭 60.

## 통계 정렬·음차 판별·형태소 분석은 근거 행이 아니라 보조 열을 만든다

병렬 말뭉치의 통계 정렬은 정렬이 없는 텍스트에 정렬을 만들어 주지만, 그 대가로 결정성이나 정밀도를 내준다. 연관 척도(Dice·로그 우도비 LLR·PMI)와 Melamed 의 경쟁 연결(competitive linking)은 순수 계수 기반이라 결정적이다. 다만 1:1 가정 때문에 다대다 연결을 못 만든다 🟡 ([Melamed 1997](https://arxiv.org/pdf/cmp-lg/9706026)). 2002 년 한 연구는 여러 척도를 비교한 뒤 LLR 임계값 9 를 택했다 🟡 ([C02-1002](https://preview.aclanthology.org/moar-dois/C02-1002.pdf)). 정렬기는 소스를 직접 열어 보니 결정성이 갈렸다. **fast_align 은 난수 호출이 없지만** `fast_align.cc:139` 의 OpenMP 합산(reduction) 때문에 다중 스레드에서는 부동소수 합산 순서가 실행마다 달라질 수 있다 🔵 ([fast_align](https://github.com/clab/fast_align/blob/cab1e9a/src/fast_align.cc)). 단일 스레드로 고정하고 두 번 돌려 해시를 비교하는 시험이 필요하다 💭 70. **eflomal 은 `/dev/urandom` 에서 시드를 읽는 깁스 표집(Gibbs sampling)이고 시드 옵션이 없어서** 기본 설정으로는 비결정적이다 🔵 ([eflomal random.c](https://github.com/robertostling/eflomal/blob/1fe2a43/src/random.c)). awesome-align·SimAlign 은 다국어 BERT 신경망 추론이다. 영–한 공개 정렬 기준과 정렬 오류율(alignment error rate)은 찾지 못했다. 유형이 가까운 일–영(KFTT)에서 fast_align 51.1, eflomal 47.5, MGIZA 48.0, awesome-align 45.6(미세조정 시 37.4)이다 🔵 ([awesome-align README](https://github.com/neulab/awesome-align/blob/5f150d4/README.md)). 그런데 영어 용어 하나를 찾는 일에는 문장 전체 정렬이 별로 필요하지 않다. Mozilla TMX 처럼 번역 단위가 짧은 UI 문자열이면, 영어 쪽에 용어가 든 단위만 골라 한국어 쪽을 세는 것으로 `breakpoint` → `중단점` 98/100 이 바로 나온다 🔵. 정렬기가 더하는 정보는 작고 결정성 비용은 크다 💭 75.

비교 말뭉치(comparable corpora) 방법은 근거 모델과 맞지 않는다. Rapp(1999)과 Fung(1995)의 문맥 벡터 + 씨앗 사전 방식은 계수 기반이라 결정적으로 만들 수 있다. 그러나 한국어 관련 연구는 정확도가 상당히 낮고 큰 씨앗 사전이 필요하다고 적는다 🟡 ([P99-1067](https://aclanthology.org/P99-1067/); [KoreaScience](https://koreascience.kr/article/JAKO201424750260684.pdf)). 무엇보다 출력이 "어느 파일 몇 줄에서 이 번역이 쓰였다" 는 근거 행이 아니라 유사도 순위다. 씨앗 사전이 곧 ko-dev-terms 의 다른 출처가 되므로 순환하기도 한다 💭 75. 단일 언어 용어 추출(term extraction, TF-IDF·TextRank 가 고전 기준선)은 "어떤 낱말이 용어인가" 를 푸는 다른 문제다 🟡 ([Springer AI & Law 2025](https://link.springer.com/article/10.1007/s10506-025-09490-6)). 영어 용어가 입력으로 주어지는 조회에는 필요하지 않다.

음차 판별(transliteration detection)은 같은 영어에 대해 음차형(`트리`)과 번역형(`트리`) 후보가 함께 생길 때 그 둘을 가르는 열을 만들 수 있다. Mozilla TMX 에서 실제로 `tree` 가 UI 에서는 `트리`, "트리 심기" 문맥에서는 `트리` 로 번역됐다 🔵. 한국어 연구로는 정길순·맹성현 외(1999)의 정보 검색용 외래어 역음차 🟡 ([IP&M 1999](https://ir.webis.de/anthology/1999.ipm_journal-ir0anthology0volumeA35A4.6/)), Kang & Choi(2000)의 결정 트리 🟡 ([LREC 2000](https://aclanthology.org/www.mt-archive.info/LREC-2000-Kang.pdf)), 음절 HMM 태깅(정밀도/재현율 80/82) 🟡 ([ResearchGate](https://www.researchgate.net/publication/220155775_A_Statistical_Model_for_Automatic_Extraction_of_Korean_Transliterated_Foreign_Words))이 있다. 이도길(2009)은 철자에서 발음을 추측하는 대신 발음 사전을 썼다 🟡 ([KoreaScience](https://koreascience.kr/article/JAKO200934939598182.pdf)). 결정적인 경로는 이렇다. CMUdict(135,166행, BSD 계열, 커밋 `7479086`)로 영어 발음을 얻고 🔵 ([cmudict](https://github.com/cmusphinx/cmudict/tree/7479086)), 국립국어원 "영어의 표기" 세칙을 옮긴 규칙표로 예상 한글을 만든 뒤, 후보와의 자모 편집 거리를 잰다 💭 60. 걸림돌은 **외래어 한글 표기 도구 Hangulize 에 40개 언어 규칙이 있지만 영어 규칙이 없다**는 점이다 🔵 재실측 ([hangulize/specs](https://github.com/hangulize/hangulize/tree/b951421/specs)). 규칙표를 직접 만들어야 한다. 용어학의 변이 유형론도 이 열의 근거가 된다. Freixa(2022)는 변이 원인을 담화적·방언적·기능적·사회언어적(언어 접촉)·인지적으로 나눈다 🟡 ([Freixa, TLRP 23](https://benjamins.com/catalog/tlrp.23.18fre)). `메서드`/`메소드` 같은 **음차끼리의 철자 변이**와 `함수`/`펑션` 같은 **음차 대 번역 변이**를 한 칸에 섞지 않을 근거가 여기서 나온다 💭 70.

형태소 분석은 이번 세션에 직접 시험했다. Kiwi(kiwipiepy 0.24.1, Apache-2.0, Windows 휠 있음)는 새 인스턴스 둘의 출력이 같았다(sha256 앞 16자 `22d0f288e743d4db`). `부수 효과를` 과 `부수효과가` 를 같은 형태소 열로 통일했다. 그러나 `콜백으로` → `콜/NNG 백/NNG`, `정점을` → `정/NNG 점/NNG` 처럼 **외래어와 미등록어를 잘못 쪼갰고**, 사용자 사전에 먼저 넣어야 고쳐진다 🔵 ([Kiwi README](https://github.com/bab2min/Kiwi/blob/bebfd76/README.md); [PyPI kiwipiepy](https://pypi.org/project/kiwipiepy/)). KoNLPy 는 GPL-3.0 이고 2022 년 이후 릴리스가 없다 🔵 ([PyPI konlpy](https://pypi.org/project/konlpy/)). 계획의 경계 규칙 v1(앞 글자가 한글이 아니고 뒤가 조사이거나 한글이 아닐 때만 센다, 조사 목록은 리소스 파일)은 조사 노트가 독립적으로 권한 "정규식 + 조사 목록, 조사를 떼지 않고 꼬리만 검사" 방식과 같다. 이 방식은 `효과` → `효`+`과` 같은 오절단이 없고 표준 라이브러리만으로 돈다. 남는 위험은 `트리이다` 의 `이다` 처럼 조사 목록에 없는 어미를 놓치는 것이다 💭 75. 형태소 분석기는 표준 라이브러리 제약과 맞지 않고 외래어 후보를 쪼개므로, 계획에 넣을 이유가 약하다.

## 기계 번역·LLM 문헌은 용어집을 소비할 뿐이지만 측정 지표는 빌려 올 수 있다

어휘 제약 디코딩(lexically constrained decoding)과 용어 인지 학습(terminology-aware training) 계열은 모두 **용어집이 이미 주어져 있다**고 가정한다. 그리드 빔 탐색(Hokamp & Liu 2017)에서 동적 빔 할당(Post & Vilar 2018, 제약 수에 대해 O(1))과 그 벡터화(Hu 외 2019)까지가 그렇다 🟡 ([N18-1119](https://aclanthology.org/N18-1119/); [N19-1090](https://aclanthology.org/N19-1090/)). Dinu 외(2019)는 기존 용어 사전 두 개를 썼고, Exel 외(2020)는 SAP 사내 용어집을 썼으며, Bogoychev & Chen(2023)은 단어 정렬로 유사 용어(pseudo-terminology)를 합성했다 🟡 ([Dinu 2019](https://ar5iv.labs.arxiv.org/html/1906.01105); [Exel 2020](https://aclanthology.org/2020.eamt-1.29); [Bogoychev 2023](https://aclanthology.org/2023.wmt-1.80)). **이 문헌 어디에도 "어떤 한국어 표기가 맞는가" 를 근거하는 절차는 없다.** ko-dev-terms 는 이들의 상류가 아니라, 이들이 소비할 용어집을 만드는 쪽에 놓인다 💭 80.

WMT 용어 공유 과제에서 **한국어가 들어간 것은 2021 년(en→ko, COVID-19, TICO-19 용어집)뿐**이다. 2023(zh→en·en→cs·de→en), 2025(en→de/es/ru/zh, 금융·IT), 2026(es→eu·en→pl·en↔zh-Hant)에는 한국어가 없다 🟡 ([WMT21 Findings](https://aclanthology.org/2021.wmt-1.69); [WMT23 Findings](https://aclanthology.org/2023.wmt-1.54); [WMT25 과제](https://www2.statmt.org/wmt25/terminology.html); [WMT26 과제](https://www2.statmt.org/wmt26/terminology.html)). WMT21 의 en→ko 점수는 본문을 열지 못해 확보하지 못했다. 과제 설계에서 얻을 시사점은 둘이다. 첫째, WMT 는 용어집이 옳은지 묻지 않고 지켰는지(adherence)만 잰다. 판정하지 않는 ko-dev-terms 와 같은 분업 위치다 💭 75. 둘째, 2023 년에는 시스템 순위가 chrF·COMET·success rate 에서는 비슷했는데 **일관성(consistency)에서만 달랐다** 🟡 ([WMT23 슬라이드](https://wmt-terminology-task.github.io/wmt_terminology_2023_slides.pdf)). 2025 년에는 일관성을 "같은 원문 용어의 번역 가운데 가장 일관된 번역에서 벗어난 비율, 정답 여부와 무관" 으로 정의해 독립 지표로 세웠다 🟡 ([WMT25 과제](https://www2.statmt.org/wmt25/terminology.html)). 정확도와 일관성이 서로 다른 축이라는 실증이다. 경고도 하나 있다. 2025 년 무작위 용어 모드의 정확도(0.77~0.96)가 정식 용어집(약 0.40~0.55)보다 높게 나왔는데, 무작위로 뽑힌 단어가 대개 일반어였기 때문이다 🟡 ([Lingua Custodia WMT25](https://arxiv.org/pdf/2510.17504)). `map`·`table` 처럼 일반어와 겹치는 개발 용어는 문자열 일치 개수가 부풀려질 수 있다 💭 70.

용어 지표는 그대로 빌려 올 만하다. 정확 일치(exact match), 창 겹침(window overlap), 1-TERm, 일관성은 모두 신경망 없이 계산되는 문자열·편집 거리 지표다. 정확 일치는 제약 용어를 문장 끝에 덧붙이는 꼼수에 약하고, 창 겹침과 1-TERm 은 참조 번역이 필요하다 🟡 ([CUNI WMT21](https://arxiv.org/html/2109.09350)). Alam 외(2021)는 BLEU 와 용어 정확 일치 사이에 약한 상관만 있다고 보고하고 평가 코드를 공개했다 🟡 ([arXiv 2106.11891](https://arxiv.org/abs/2106.11891)). ko-dev-terms 에 직접 맞는 것은 **Semenov & Bojar(2022)의 일관성 지표**다. 참조 번역 없이 텍스트 전체에서 용어 번역의 일관성과 비모호성을 잰다 🟡 ([2022.wmt-1.41](https://aclanthology.org/2022.wmt-1.41)). 괄호 병기나 번역 단위처럼 정렬이 공짜로 얻어지는 문장에서 "같은 영어 → 한국어 표기 몇 갈래, 최빈 표기 비율" 을 재는 데 그대로 쓸 수 있다. 승자를 고르지 않고 분산만 수치로 보이므로 판정 금지와도 양립한다 💭 70. 이 지표는 일관되게 틀린 번역에도 만점을 준다. 그래서 정답 표시로 쓰면 안 되고, 분포를 보여 주는 열로만 써야 한다.

LLM 은 용어 판정자로 쓸 수 없다는 증거가 쌓여 있다. 프롬프트에 사전 대역어를 넣는 DiPMT 🟡 ([arXiv 2302.07856](https://ar5iv.labs.arxiv.org/html/2302.07856)), 용어가 빠진 번역만 LLM 이 고치는 방식(필요 용어 출현율 36.67% → 72.88%) 🟡 ([Moslem 2023](https://aclanthology.org/2023.wmt-1.82))은 모두 효과를 보였다. 그러나 저자들 스스로 이를 "**소프트 제약(soft constraint)**" 이라 부른다. LLM 이 제약을 반드시 반영한다는 보장이 없기 때문이다 🟡 ([Bogoychev & Chen 2023](https://aclanthology.org/2023.wmt-1.80)). 모호한 용어에서는 GPT-4.1 에 용어 사전을 주자 정확도가 43.5% → 37.1% 로 떨어졌다는 보고가 있다(실험 조건 미확인) 🟡 ([arXiv 2507.03580](https://arxiv.org/pdf/2507.03580)). Li 외(2025)는 도메인 적응 번역에서 **검색(retrieval)이 생성(generation)보다 일관되게 낫다**고 보고했다. 계획이 검색된 근거를 1차로 두고 LLM 후보를 표지 붙은 2차로 두는 설계를 가장 직접 지지하는 실험이다. 단 그 실험이 잰 것은 번역 품질이지 표기 근거가 아니다 🟡 ([arXiv 2503.05010](https://arxiv.org/html/2503.05010v1)). en–ko 직접 근거는 두 건이다. 괄호 병기 용어 번역(Parenthetical Terminology Translation, Myung 외 2024)은 `fine-tuning` 이 `파인튜닝`/`미세조정` 으로 갈리는 불일치를 동기로 삼았다. 하지만 데이터 1,398쌍을 GPT 계열 에이전트가 생성했으므로 계획 기준으로는 "LLM (추론)" 행이지 근거 말뭉치가 아니다 🟡 ([arXiv 2410.00683](https://arxiv.org/html/2410.00683v1)). WMT24 의 ja→ko 특허 번역에서는 ChatGPT 가 용어집 항목을 적용하지 못하고 일본어 용어를 그대로 내기도 했다 🟡 ([WMT24](https://www2.statmt.org/wmt24/pdf/2024.wmt-1.51.pdf)). 환각(hallucination)은 저자원 방향과 **영어에서 나가는 방향**에 몰린다 🟡 ([Guerreiro 외, TACL 2023](https://aclanthology.org/2023.tacl-1.85)). 그러나 **en→ko 에서 LLM 의 용어집 준수율이나 용어 환각률을 정량화한 연구는 찾지 못했다.** 개발 문서의 `backpressure` 를 기계공학 용어 `배압` 으로 옮긴 사례 🟡 ([GitHub 이슈](https://github.com/nil-park/claude-workflow-kit/issues/11))는 다른 도메인에 이미 자리 잡은 한국어로 직역되는 오류의 전형이다. 개발 말뭉치 빈도 0 과 다른 도메인 빈도의 대비 자체가 측정 가능한 신호가 된다 💭 60.

결정성 문제는 원리적이다. "결정적으로 설정한" LLM 5개를 10회씩 돌리자 정확도가 최대 15% 요동했다 🟡 ([Atil 외](https://arxiv.org/abs/2408.04667)). 원인은 서버 부하에 따라 바뀌는 배치 크기와 배치 불변(batch invariant)이 아닌 추론 커널로 분석됐다 🟡 ([Thinking Machines 요약](https://simonwillison.net/2025/Sep/11/defeating-nondeterminism)). 제공자 문서도 같은 말을 한다. OpenAI 는 시드를 줘도 "(대체로) 일관된" 출력일 뿐 결정성은 보장되지 않는다고 하고 🟡 ([OpenAI Cookbook](https://developers.openai.com/cookbook/examples/reproducible_outputs_with_the_seed_parameter)), Azure 는 변동이 "드물지 않다" 고 하며 🟡 ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reproducible-output)), Anthropic SDK 참조는 "온도 0.0 에서도 완전히 결정적이지 않다" 고 적는다 🟡 ([anthropic-sdk-ruby](https://rubydoc.info/github/anthropics/anthropic-sdk-ruby/main/Anthropic%2FModels%2FBeta%2FMessageCreateParams:temperature)). 로컬 vLLM 의 배치 불변 모드는 베타이고 GPU 조건이 붙는다 🟡 ([vLLM 문서](https://docs.vllm.ai/en/stable/features/batch_invariance/)). 그러므로 LLM 후보 행의 재현성은 재생성이 아니라 **기록된 원응답을 다시 검증하는 방식**으로만 확보할 수 있다. 검증 단계(말뭉치 개수)는 스냅숏 해시만 같으면 결정적으로 재현된다 💭 85. "LLM 이 후보를 내고 결정적 단계가 말뭉치로 확인한다" 와 똑같은 출판 사례는 찾지 못했다. 가장 가까운 것은 결정적 탐지(정렬 검사·누락 검사) 뒤에 생성적 수리(재디코딩·사후 편집)를 붙인 WMT 시스템들이다. ko-dev-terms 는 이 구조에서 수리를 버리고 탐지만 남긴 형태다 💭 70.

FineWeb-2 는 후보로 남길 수 있지만, 94.73 GB 를 한 번 추출하는 비용을 정당화하려면 먼저 K1·K2 가 메우지 못하는 공백의 크기를 재야 한다 💭 65. 계획이 이미 택한 것 가운데 이번 조사로 근거가 더해진 것도 있다. 정규식 + 조사 목록 경계 규칙, 0 을 0 으로 내기, 판정하지 않기(WMT 도 준수만 잰다), ① 과 ② 의 분리(Kim 2023)가 그렇다.

## 결론

이번 조사가 바꾼 이해는 "근거" 를 **정렬이 어디서 왔는가**의 문제로 다시 쓸 수 있다는 점이다. 번역 단위 정렬(번역 메모리), 저자 정렬(괄호 병기), 링크 정렬(지식 기반), 정렬 없음(원시 빈도)은 서로 다른 강도의 증거다. 증거 행의 종류를 이 넷으로 나누면, 지금 계획의 ①·② 구분보다 한 단계 더 정확하게 "이 수가 무엇을 말하고 무엇을 말하지 않는가" 를 행마다 밝힐 수 있다. 또 하나 분명해진 것은, 학계 어느 쪽도 "어떤 한국어 표기가 맞는가를 재현 가능하게 근거하기" 를 풀지 않았다는 사실이다. 기계 번역 문헌은 용어집을 주어진 것으로 두고 준수만 잰다. 국어학과 용어학은 설문과 포털 검색으로 정착을 잰다. 고정된 스냅숏 위에서 정렬된 근거를 세는 ko-dev-terms 의 방식은 이 빈칸에 해당한다.

실무적으로 가장 중요한 함의는 공백의 위치다. 실측으로 확인한 원천은 도구·프레임워크 어휘에 몰려 있고, `postcondition` 같은 공학 개념 어휘에서는 비어 있다. 그래서 시범(8절 6단계)에서는 '근거 없음' 이 바로 이런 용어에서 가장 자주 나올 것으로 예상된다 💭 70. 그 비율과 분포가 ③·④ 를 정할 핵심 재료가 된다. 이 공백을 메울 후보는 하필 이번 세션에서 열지 못한 곳들이다. 그러므로 다음 측정의 우선순위는 새 방법을 고안하는 것이 아니라, 네트워크 허용 목록에 `dumps.wikimedia.org` · `opendict.korean.go.kr` · `kli.korean.go.kr` · `aclanthology.org` · `arxiv.org` 를 더해 막힌 원천의 수록량을 한 번 실제로 세는 일이다. 허용 목록에 넣을지는 계획 6절의 클라우드 설정과 함께 사용자가 정한다.
