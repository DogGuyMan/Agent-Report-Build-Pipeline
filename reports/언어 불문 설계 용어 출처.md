# 계획의 네 출처는 설계 어휘를 비워 둔다

ko-dev-terms 계획에 이미 있는 네 출처 가운데 언어 불문 설계·소프트웨어 공학 어휘를 의미 있게 덮는 것은 **Microsoft Terminology Collection 하나뿐**이다. 쿠버네티스(Kubernetes)·MDN·python-docs-ko 세 용어집(glossary)을 합쳐도 탐침(probe) 63개 가운데 **의도한 설계 의미로 들어 있는 것은 5개(전부 MDN)** 다 🔵. Microsoft 모음은 프랑스어·독일어판을 대리로 재 보니 63개 중 36개가 영어 표제로 있었지만, 그중 13개는 coupling = CRM 레코드 연결처럼 **설계가 아닌 뜻으로만** 들어 있었고 한국어판 자체는 받지 못했다 🔵. 넷을 다 두어도 SOLID 다섯 원칙, 의존성 주입(dependency injection), 제어의 역전(inversion of control), 코드 스멜(code smell), 바운디드 컨텍스트(bounded context)의 근거는 0이다. 한국어 짝을 담은 출처 중에는 여섯 기준을 모두 넘는 곳이 없다. ktword.co.kr 는 허락이 가장 넓고(출처 표시만 하면 상업 이용 포함) 저자가 영어 원어를 직접 붙이지만, 일괄 경로가 없고 소프트웨어 공학 층이 얇다(탐침 16개 중 6~7개, 🟡). 한국어 위키백과는 범위가 가장 넓지만(개념어 26개 중 약 20개, 🟡) 동일조건변경허락(CC BY-SA)이고 이번 세션에서는 열리지 않았다. 기계 판독·고정·라이선스가 모두 깨끗한 곳은 `dahlia/cjk-compsci-terms` 하나인데 범위가 가장 좁다 🔵. 영어 쪽에서 유일한 국제 표준 어휘(de jure)인 ISO/IEC/IEEE 24765 와 그 무료판 SEVOCAB 은 내보내기(export)가 확인되지 않아 손 조회 기록 꼴로만 쓸 수 있다 🟡. 기계로 고정할 수 있는 범위 목록은 iSAQB 소프트웨어 아키텍처 용어집(CC BY 4.0, 영어 표제어 274개)과, 이름만 옮겨 적는 닫힌 목록(GoF·SOLID·패키지 원칙·GRASP)이다 🔵/🟡. 이 둘을 합쳐도 탐침 63개 중 33개는 SEVOCAB 확인이나 사용자 목록에 기대야 한다. 게다가 한국어 근거가 가장 얇은 postcondition·call graph·technical debt·code smell 이 영어 쪽 열린 목록에서도 빈다 — **공백은 번역 자원만의 문제가 아니라 범위 목록 쪽에서도 열려 있다.** 탐침 목록은 조정자(coordinator)가 고른 연구 도구이지 정답이 아니다. 남은 공백 대부분은 막힌 호스트 몇 개(`www.computer.org` · `download.microsoft.com` · `dumps.wikimedia.org` · `www.ktword.co.kr`)를 열면 한 번의 측정으로 메울 수 있다.

## 탐침 목록은 연구 도구이고, 근거는 실측과 검색 요약으로 갈린다

이 보고서의 "적중" 은 세 가지 탐침 목록을 기준으로 센 값이다. 계획의 기존 출처를 잰 **63개 목록**(side effect … pipeline, `research_notes/언어 불문 설계 용어 출처/scripts/probe.json`), 한국어 표기 출처를 잰 **49개 목록**(개념어 26개 + GoF 패턴 이름 23개), 국제 영어 어휘와 ktword 를 잰 **16개 목록**이다. 셋 다 조정자가 연구 도구로 고른 것이고, ko-dev-terms 의 범위나 정답(ground truth)이 아니다. 63개 목록에는 `edge` · `node` · `tree` · `stage` · `layer` 처럼 여러 분야가 함께 쓰는 일반어가 섞여 있어서, "표제 적중" 과 "의도한 설계 의미로 적중" 을 따로 셌다. 목록이 바뀌면 이 보고서의 비율도 모두 바뀐다. 표제 적중은 결정적(deterministic) 규칙으로 셌다. 영어 표제를 소문자로 바꾸고 `_` · `-` · `/` 를 공백으로 바꾼 뒤 끝의 `s`/`es` 를 떼어 **완전 일치**할 때만 셌고, 부분 포함은 따로 셌다. 본문 괄호 병기는 머리말·코드 블록·인라인 코드·Hugo shortcode·MDN 매크로·HTML 주석을 뺀 산문에서 `한글 1~4어절 + (탐침 영어)` 꼴만 셌고, `.po` 파일은 `msgstr` 만 봤다 🔵. 항목을 플랫폼 고유(P), 일반 IT(G), 언어 불문 일반 프로그래밍(S1), 언어 불문 설계·공학(S2)으로 나눈 판정은 한 연구자의 판단이다(💭 65~80). 교차 검증은 하지 않았고, S2 목록은 스크립트 `classify.py` 에 공개돼 있어 다시 판정할 수 있다.

근거 표지는 셋이다. **🔵 실측**은 이번 세션에 원천을 직접 받아 센 값이다. GitHub 공개 저장소를 익명 `git clone` 으로 커밋 고정해 받았고, Microsoft Learn 문서는 Microsoft Learn MCP 로 원문을 읽었다. 이 보고서를 쓰는 중에 iSAQB 용어집(영어 표제어 274개), cjk-compsci-terms(항목 259개, 모두 한국어 있음), Azure 클라우드 디자인 패턴 표(44행, `LICENSE` = CC BY 4.0)를 같은 커밋으로 다시 받아 같은 값을 얻었다. iSAQB 와 cjk-compsci-terms 를 63개 목록에 맞춘 값은 이때 새로 쟀다(아래 "재실측"). **🟡 요약**은 원문이 막혀 검색 결과에만 기댄 것이다. 이 세션의 웹 검색은 원문 스니펫(snippet)이 아니라 **검색 도구가 요약한 글**을 돌려주므로, 요약 안의 따옴표 인용도 원문 그대로라는 보장이 없다. **💭 추론**은 위 둘에서 끌어낸 판단이고, 붙은 정수가 확신도다. 막힌 호스트는 보고서 작성 시점에 다시 접속해 봐도 16곳 모두 연결 실패(HTTP 코드 000)였다 🔵. `www.ktword.co.kr` · `pascal.computer.org` · `www.computer.org` · `obp.iso.org` · `download.microsoft.com` · `refactoring.guru` · `ko.wikipedia.org` · `dumps.wikimedia.org` · `standard.go.kr` · `www.ncs.go.kr` · `terms.tta.or.kr` · `cockpit.ireb.org` · `wikidocs.net` · `martinfowler.com` · `domainlanguage.com` · `www.enterpriseintegrationpatterns.com` 이 그것이다. GitHub 검색 API 도 "sessions are bound to their configured repositories" 로 막혀 있었다 🔵. 그래서 **ktword·SEVOCAB·SWEBOK·ISO·한국어 위키백과·refactoring.guru·국내 표준에 관한 사실은 전부 🟡** 다.

## 계획의 세 저장소 용어집은 설계 의미로 다섯 낱말만 덮는다

**쿠버네티스 한국어 용어집**(`kubernetes/website` 커밋 `ed70e311`, 2026-10-26)은 항목 123개 가운데 **105개(85.4%)가 쿠버네티스 고유이고 설계·공학(S2) 항목은 0개**다 🔵 ([glossary](https://github.com/kubernetes/website/tree/ed70e311737a341574ed5758b7af24e3bba232cb/content/ko/docs/reference/glossary)). 63개 탐침 중 표제 완전 일치는 `node → 노드` 하나인데, 정의가 "쿠버네티스의 작업 장비(worker machine)" 라서 그래프의 노드(node)가 아니다 🔵 ([node.md](https://github.com/kubernetes/website/blob/ed70e311737a341574ed5758b7af24e3bba232cb/content/ko/docs/reference/glossary/node.md)). **MDN 한국어 용어집**(`mdn/translated-content` 커밋 `2a7c03a4`)은 항목 564개 가운데 플랫폼 고유가 325개(57.6%), S2 가 37개(6.6%)다. 의도한 설계 의미로 맞은 것은 `abstraction → 추상화` · `encapsulation → 캡슐화` · `idempotent → 멱등성` · `inheritance → 상속` · `polymorphism → 다형성` 다섯이다 🔵 ([MDN glossary](https://github.com/mdn/translated-content/tree/2a7c03a449507969b925ac954f41c340d7c50263/files/ko/glossary)). **python-docs-ko `glossary.po`**(브랜치 3.14, 커밋 `242bdce6`)는 표제 약 148개 가운데 S1 이 58.1%, 플랫폼 고유가 34.5% 다. 탐침과 맞은 것은 `decorator → "decorator (데코레이터)"` 하나인데, 이것도 Python 의 `@` 문법이지 GoF 데코레이터 패턴이 아니다 🔵 ([glossary.po:777-788](https://github.com/python/python-docs-ko/blob/242bdce63d20a3042fa438fea9677f289d7a6d0c/glossary.po)). 이 파일에는 읽기 함정이 둘 있다. `#, fuzzy` 표제 다섯 개는 번역이 다른 항목에서 잘못 복사됐고(`walrus operator → "asynchronous iterator (비동기 이터레이터)"`), 3.14 신규 표제 여섯 개는 `msgstr` 이 비어 있다 🔵.

계획의 말뭉치(②) 갈래로 보면 사정이 더 나쁘다. 세 저장소 본문에서 탐침이 `한글(English)` 꼴로 병기된 것은 저장소마다 14~19건이고, 각 저장소 병기 전체의 0.6~0.7% 다. **63개 중 43개는 세 말뭉치 어디에도 병기가 없다** 🔵. single responsibility · open-closed · Liskov substitution · interface segregation · dependency inversion · common closure principle, inversion of control, code smell, bounded context, ubiquitous language 는 병기도 0이고, 한국어 후보(단일 책임 원칙 · 제어의 역전 · 코드 스멜 · 바운디드 컨텍스트 · 유비쿼터스 언어)의 원시 개수도 0이다 🔵. 원시 한국어 개수가 큰 낱말도 있다(Python 본문의 `부작용` 52 · `호출자` 162). 그러나 이 개수에는 의미 구분이 없고, 뒤 경계 규칙을 적용하지 않아 과다 집계다.

진짜 위험은 플랫폼 종속 그 자체보다 **동형이의(homonym)** 다. 같은 영어 표제가 플랫폼 의미로 들어 있다. node 는 쿠버네티스 장비·DOM·네트워크이고, decorator 는 Python 문법, inheritance 는 MDN 본문에서 주로 CSS 상속, bisect 는 Python `bisect` 모듈이다 🔵. 💭 80 — 증거 행에 출처 이름만 적고 정의나 의미 표지를 싣지 않으면, 쓰는 LLM 이 "노드 = 확립된 용어" 를 그래프 문맥에 잘못 옮겨 쓸 수 있다.

### Microsoft 용어 모음은 23개를 덮지만 13개는 다른 뜻으로만 덮는다

Microsoft Learn 은 이 모음을 Microsoft 제품과 통합되는 애플리케이션의 현지화용이자 "base IT glossary for language development in the nearly 100 languages" 로 소개한다 🔵 ([Microsoft Terminology](https://learn.microsoft.com/globalization/reference/microsoft-terminology)). 한국어 TBX 는 `download.microsoft.com` 이 막혀 받지 못했다. 그래서 같은 모음을 Xbench 로 xlsx 로 바꾼 제3자 자료 `spidersouris/termic-data`(보관됨, 커밋 `af955ef`, 2023-07-04)의 프랑스어·독일어판을 영어 쪽 대리(proxy)로 쟀다. 이 자료에는 11개 언어가 있지만 한국어는 없다 🔵 ([termic-data](https://github.com/spidersouris/termic-data/tree/af955efdeab80e42452c435428d4d7077008b917/data); [termic README](https://github.com/spidersouris/termic/tree/6e4fe2a5b80f2efd06e117db19037aa6c207fe55)). 프랑스어판은 36,647행에 영어 표제 33,909개이고, **고유명사(Proper Noun)가 31.1%**, 정의·표제·품사 중 하나라도 Microsoft 제품 표지가 걸리는 항목이 40.8% 다 🔵. 탐침 63개 중 **36개(독일어판 35개)가 표제로 있어** 넷 중 압도적으로 많다 🔵. 정의(`def_en_US`)로 의미를 확인하면 23개는 설계·프로그래밍 뜻의 행을 하나 이상 갖는다. cohesion("The degree to which the elements of a module belong together"), side effect, polymorphism, design pattern, refactoring, technical debt, ubiquitous language, circular dependency, call graph 가 여기 든다. 나머지 **13개는 다른 뜻으로만 있다**: coupling(CRM 레코드 연결), encapsulation(네트워크 프로토콜), inheritance(ACL 상속), singleton(고정 자원 데이터베이스 인스턴스), decorator(WPF 스타일 컨트롤), strategy(게임 장르), adapter(하드웨어 카드), caller(전화 거는 사람) 등이다 🔵 측정 / 💭 80 의미 판정. 없는 27개에는 SOLID 다섯, 의존성 주입, 제어의 역전, 정보 은닉(information hiding), abstraction, 관심사 분리(separation of concerns), observer, facade, visitor, code smell, bounded context 가 있다 🔵. 💭 60 — 한국어판의 표제 집합이 프랑스어판과 같은지는 모른다(베트남어판은 17,561행으로 절반이다). 한국어 현지화 스타일 가이드는 `aka.ms/korean-styleguide` 로 연결되지만 PDF 를 열지 못했다 🔵 ([Localization Style Guides](https://learn.microsoft.com/globalization/reference/microsoft-style-guides)). 검색 요약에 따르면 이 가이드는 표준국어대사전을 기준 사전으로 들고 나머지 용어는 Microsoft Terminology 를 보라고 한다. 음역·병기 규칙은 요약에 나오지 않았다 🟡 ([kor-kor-StyleGuide.pdf](https://download.microsoft.com/download/5/b/6/5b62389f-4e3b-4c77-bc18-94efba2fa7bb/kor-kor-StyleGuide.pdf)).

### 측정은 Microsoft 를 지지하고 쿠버네티스 용어집은 지지하지 않는다

사용자는 앞서 Microsoft 와 쿠버네티스를 두는 쪽으로 기울었다. 측정 숫자는 그중 **Microsoft 쪽은 지지하고 쿠버네티스 용어집 쪽은 지지하지 않는다**. 이 결론은 무언가를 빼자는 쪽이라서, 저장소의 기각 검사표(`docs/overturn/README.md`)에 대어 봤다. 첫째로 "플랫폼 종속" 이라는 반대 근거는 Microsoft 에도 똑같이 있다(고유명사 31%). 그러므로 플랫폼 종속은 두 출처를 가르는 근거가 아니다. 가르는 것은 설계 의미의 적중이다(23 대 0). 둘째로 "빼느냐 두느냐" 는 사용자가 정한 방향 — 무게는 **범위와 우선순위이지 판정이 아니다** — 아래에서는 양자택일이 아니다. 쿠버네티스 용어집을 맨 아래 우선순위 층에 "클라우드" 범위 표지를 달아 남기는 셋째 안이 있다. 셋째로 사용자가 쿠버네티스를 두려던 동기가 "번역 공동체의 결정 이력" 이라면, 그 가치는 툴팁용 `glossary/*.md` 가 아니라 한글화 가이드 `localization_ko.md` 에 있다. 이 문서에는 257행 용어 표가 있고, 155~171행이 우선순위를 "한글 단어(순우리말 > 한자어·외래어) > 한영 병기(예: 훅(hook)) > 영어 단어" 로, 한영 병기를 "페이지 내에서 처음 사용될 때 1회" 로 못박는다. 254~271행은 이 표가 "쿠버네티스 문서 한글화팀 회의를 통해 결정" 된다고 적는다 🔵 ([localization_ko.md](https://github.com/kubernetes/website/blob/ed70e311737a341574ed5758b7af24e3bba232cb/content/ko/docs/contribute/localization_ko.md)). 다만 이 표도 클라우드 중심이라 63개 탐침 중 3개만 맞는다. 💭 70 — MDN 은 S2·S1 갈래(196개)만 남기면 의도한 설계 의미 다섯을 모두 지키면서 웹 표준·제품 이름 325개를 덜어 낸다. 💭 65 — python-docs-ko 용어집은 설계 의미 적중이 0이고 fuzzy 오역이 있어 권위 출처(①)로는 약하다. `msgstr` 본문의 일반 컴퓨터 과학 어휘 빈도는 말뭉치 ② 로 쓸모가 남는다.

"본 웹사이트 내 모든 저작물은 원출처를 밝히는 한 자유롭게 사용(상업화포함) 가능합니다" 🟡 ([ktword](http://www.ktword.co.kr/)). **영어 짝 꼴이 ko-dev-terms 의 "고르지 않고 나열" 모델과 잘 맞는다.** 옛 항목은 표제에 영어 하나와 한국어 여럿을 저자가 직접 나열한다("Life Cycle 순기, 생명 주기, 라이프 사이클") 🟡 ([no=1200](http://www.ktword.co.kr/test/view/view.php?no=1200)). 그러나 소프트웨어 공학 항목은 표제가 한국어뿐이고("소프트웨어 설계" · "모듈" · "부수 효과 [전산]"), 영어는 본문 괄호에 있다("결합도 (Coupling)", "단일 책임의 원칙 (Single Responsibility Principle, SRP)") 🟡 ([no=6552](http://www.ktword.co.kr/test/view/view.php?no=6552); [no=2226](http://www.ktword.co.kr/test/view/view.php?no=2226)). 16개 탐침 중 소프트웨어 공학 의미로 잡힌 것은 6~7개다(side effect · coupling · cohesion · SRP · DIP · 디자인 패턴/옵저버 · 계층형 아키텍처). 독립 항목은 "부수 효과 [전산]" 하나뿐이고, 나머지는 개요 항목 안의 한 줄이다 🟡 ([no=6742](http://www.ktword.co.kr/test/view/view.php?no=6742); [no=6543](http://www.ktword.co.kr/test/view/view.php?no=6543)). postcondition · invariant · circular dependency · call graph · technical debt · code smell · refactoring 은 검색 색인에 잡히지 않았고, idempotent 는 수학 뜻(집합 연산·부울 대수)으로만 나왔다 🟡. 항목은 정수 번호로 식별된다(`view.php?no=N` · `m_temp1=N` · `abbr_view.php` 세 꼴이 같은 N) 🟡. ### 위키백과가 가장 넓고, cjk-compsci-terms 가 가장 깨끗하다

**한국어 위키백과**는 49개 목록의 개념어 26개 가운데 약 20개의 한국어 표제나 첫 문장 병기가 검색으로 확인됐다(스니펫에 나온 것만 센 하한) 🟡. 결합도 문서는 "결합도(coupling)는 모듈 간의 상호 의존 정도", 호어 논리 문서는 "P는 전제 조건(precondition), Q는 사후 조건(postcondition)" 처럼 첫 문장이 짝을 준다 🟡 ([결합도](https://ko.wikipedia.org/wiki/%EA%B2%B0%ED%95%A9%EB%8F%84); [호어 논리](https://ko.wikipedia.org/wiki/%ED%98%B8%EC%96%B4_%EB%85%BC%EB%A6%AC)). 리팩터링, 코드 스멜, 기술 부채, 호출 그래프도 표제로 있다 🟡 ([코드 스멜](https://ko.wikipedia.org/wiki/%EC%BD%94%EB%93%9C_%EC%8A%A4%EB%A9%9C); [기술 부채](https://ko.wikipedia.org/wiki/%EA%B8%B0%EC%88%A0_%EB%B6%80%EC%B1%84)). **같은 개념이 문서마다 다르게 옮겨진다.** 리스코프 치환 원칙 문서는 "선행조건 … 후행조건 … 불변조건" 이라 쓰고, 호어 논리 문서는 "전제 조건 … 사후 조건" 이라 쓴다. 제어의 역전도 `제어 반전` 과 `역제어` 로 갈린다 🟡 ([리스코프 치환 원칙](https://ko.wikipedia.org/wiki/%EB%A6%AC%EC%8A%A4%EC%BD%94%ED%94%84_%EC%B9%98%ED%99%98_%EC%9B%90%EC%B9%99); [의존성 주입](https://ko.wikipedia.org/wiki/%EC%9D%98%EC%A1%B4%EC%84%B1_%EC%A3%BC%EC%9E%85)). `부작용` 표제는 의학 문서이고, 컴퓨터 과학 뜻은 `부작용 (컴퓨터 과학)` 이라는 분류어 붙은 표제로 따로 있다 🟡 ([부작용](https://ko.wikipedia.org/wiki/%EB%B6%80%EC%9E%91%EC%9A%A9)). 인터페이스 분리 원칙 단독 문서, 계층형 아키텍처, circular dependency, deterministic, bounded context, ubiquitous language 는 스니펫에 나오지 않았고, 넘겨주기(redirect)는 하나도 확인하지 못했다. 덤프는 CC BY-SA 4.0 + GFDL 이고 날짜로 고정할 수 있다 🟡. 💭 70 — 위키백과는 문서 단위로 행을 내야 하고(같은 위키백과 안에서도 표기가 갈린다), 동음이의 표제는 분류어를 함께 실어야 의미가 유지된다.

**`dahlia/cjk-compsci-terms`**(커밋 `65a7584`, 2026-10-19, CC BY-SA 4.0)는 YAML 표 28개에 항목 259개가 있고 **259개 모두에 한국어가 있다** 🔵 재실측 ([cjk-compsci-terms](https://github.com/dahlia/cjk-compsci-terms/tree/65a7584c56df0757342632a5e567384ae739ed33)). 스키마가 있어 결정적으로 읽힌다. 한국어는 음차형(`{term: 싱글톤, loan: singleton}`)과 한자형(`依存性 注入` 에 `read: 의 존 성` + `주 입`) 두 꼴이라서, 한자형은 `read` 를 이어 붙여야 한글 표기가 나온다 🔵 ([design-patterns.yaml](https://github.com/dahlia/cjk-compsci-terms/blob/65a7584c56df0757342632a5e567384ae739ed33/tables/design-patterns.yaml)). 범위는 좁다. 49개 목록에서 정확히 맞은 것은 7개(의존성 주입 · 리팩토링 · 싱글톤 · 옵저버 · 어댑터 · 데코레이터 · 전략)다 🔵. 63개 목록에 맞추면 13개인데, 그중 넷(node · vertex · tree · pipeline)은 일반 컴퓨터 과학 어휘다 🔵 재실측. `architecture.yaml` 은 소프트웨어 아키텍처가 아니라 컴퓨터 구조(instruction set · register)다 🔵.

## 영어 쪽 범위는 국제 표준을 손으로, 닫힌 목록을 기계로 정한다

**ISO/IEC/IEEE 24765(Systems and software engineering — Vocabulary)** 는 소프트웨어 공학 어휘의 유일한 국제 표준이다. 현행판은 2017년 2판이고 영어만 있다 🟡 ([IEC webstore](https://webstore.iec.ch/publication/61433)). 3판(ISO 92875)이 진행 중인데, 단계 표기가 출처마다 엇갈린다(2025-09 "DIS → FDIS" 대 2026 초 "CD 공개 검토") 🟡 ([ISO 92875](https://www.iso.org/standard/92875.html)). 같은 내용은 IEEE Computer Society 와 ISO/IEC JTC 1/SC 7 이 **SEVOCAB** 으로 무료 공개하고, 24765 는 이 데이터베이스의 주기적 스냅숏으로 발행된다 🟡 ([SEVOCAB](https://www.computer.org/sevocab)). SEVOCAB 은 용어별·출처 표준별 검색을 주지만 파일 내보내기나 API 는 찾지 못했다 🟡 ([Using SEVOCAB](https://pascal.computer.org/sev_display/help.jsp)). 정의 복사는 "출처를 밝히는 한" 허용된다는 문구가 판매처 요약에만 2차 인용으로 보인다 🟡 ([iTeh](https://iteh.es/catalog/standards/iso/8a918aae-6e85-410f-b166-4b076301f461/iso-iec-ieee-24765-2017)). 항목 수는 어느 출처에도 없었다. 16개 탐침 중 수록이 확인된 것은 coupling("The manner and degree of interdependence between software modules")과 cohesion 둘뿐이고, 그것도 제3자 매뉴얼의 인용으로 확인했다 🟡 ([Squoring coupling](https://support.squoring.com/documentation/16.3/reference_manual/ch07s67.html); [Squoring cohesion](https://support.squoring.com/documentation/16.3/reference_manual/ch07s39.html)). 💭 75 — 지금 24765/SEVOCAB 을 쓸 수 있는 꼴은 TTA 와 같은 **손 조회 기록**(조회 날짜 · 24765:2017 · 출처 표준 표기)뿐이다. 정의 없이 용어 이름만 저장하면 위험이 더 낮다. **SWEBOK Guide v4.0a**(2025-09-25 수정)는 이메일 양식으로 무료로 받지만, 미러로 확인한 저작권 면은 "All rights reserved" 이고 무료 사본을 개인·학술용으로 한정한다 🟡 ([SWEBOK](https://www.computer.org/education/bodies-of-knowledge/software-engineering); [studylib 미러](https://studylib.es/doc/9522264/guide-to-the-software-engineering-swebok-v4)). 용어집이 있는지는 확인하지 못했다. 💭 60 — SWEBOK 은 정의 사전이 아니라 지식 영역(knowledge area) 18개의 주제 체계다. 그래서 "어느 영역에 속하는가" 를 가르는 범위 축으로 쓰는 편이 자연스럽다. Kehrer 외(2025)가 SWEBOK v3 의 지식 영역을 용어 목록의 기준으로 삼은 선례가 있다 🟡 ([arXiv 2507.02665](https://arxiv.org/html/2507.02665v1)). **ISO/IEC 2382:2015** 는 영어·프랑스어 정보기술 일반 어휘이고, Online Browsing Platform 에서 "열람 무료, 내려받기 불가" 다 🟡 ([ANSI ISOT Guidance Note 010](https://share.ansi.org/ISOT/ISOT%20Guidance%20Notes/ISOT%20Guidance%20Note%20010%20-%20ISO's%20Online%20Browsing%20Platform.pdf)). 오프라인 고정과 정면으로 충돌하고 설계 범위와도 맞지 않는다. **IEEE 610.12-1990** 은 24765 로 대체됐다 🟡 ([IEEE SA](https://standards.ieee.org/ieee/610.12/855)).

기계 판독·커밋 고정·공개 라이선스를 실측으로 모두 확인한 범위 목록은 **iSAQB "Glossary of Software Architecture"** 다. 커밋 `bd3ce64`(2026-10-09), 판 `2024.1` 에 파일 275개, **영어 표제어 274개**가 있고 라이선스는 CC BY 4.0 이다 🔵 재실측 ([isaqb-org/glossary](https://github.com/isaqb-org/glossary/tree/bd3ce64e1f4a250ccd1806719723ff80b7202cb8); [04-license.adoc](https://github.com/isaqb-org/glossary/blob/bd3ce64e1f4a250ccd1806719723ff80b7202cb8/docs/0-preamble/04-license.adoc)). 파일마다 영어·독일어 정의가 함께 있어서 의미 표지로도 쓸 수 있다. 16개 탐침 중 8개(Layer 까지 치면 9개)가 표제어로 있고, 63개 목록에 맞추면 **27개**다 🔵 재실측. 이 값은 괄호 안 약어를 떼고 셌고, 동형이의 `Node (Node.js)` · `Node (in UML)` 는 뺐으며, 이름이 다른 `Open-Close-Principle (OCP)` 은 넣었다. SOLID 다섯과 패키지 원칙 여섯은 표제어로 모두 있고, GoF 23개 중 11개가 있으며, GRASP 9개는 하나도 없다 🔵. 다만 이것은 국제 표준이 아니라 **국제 자격 인증 단체의 공동체 용어집**이고, 언어는 영어·독일어뿐이다 🔵. 닫힌 목록은 크기가 작고 이름이 고정돼 있다. GoF 23개(생성 5 · 구조 7 · 행위 11), SOLID 5개, 패키지 원칙 6개(REP · CCP · CRP · ADP · SDP · SAP), GRASP 9개는 사람이 손으로 옮겨 적으면 된다 🟡 ([GRASP 강의 자료](https://handin-ps.informatik.uni-tuebingen.de/teaching/ss18/se/5_grasp.pdf); [Sitecore Helix 패키지 원칙](https://helix.sitecore.com/appendix/package-principles.html)). 미국 저작권청 Circular 33 은 이름·짧은 문구가 저작권 보호를 받지 못한다고 밝힌다(정의 본문은 별개이고, 한국법 판단은 하지 않았다) 🟡 ([Circular 33](https://www.copyright.gov/circs/circ33.pdf)). 분산·통합 쪽 목록도 있다. Azure 클라우드 디자인 패턴 44개는 CC BY 4.0 이고 커밋 `6d1df20` 으로 고정된다 🔵 재실측 ([index.md](https://github.com/MicrosoftDocs/architecture-center/blob/6d1df20e7433ce2b765b4944c10a3ed0f9625caf/docs/patterns/index.md)). EIP 65개는 이름·문제/해법 문장이 CC BY 다 🟡 ([EIP](https://www.enterpriseintegrationpatterns.com/eaipatterns.html)). Evans 의 DDD Reference(2015)는 CC BY 4.0 이다 🟡 ([DDD Reference](https://domainlanguage.com/ddd/reference/)). `iluwatar/java-design-patterns` 는 패턴 192개(MIT)를 담지만 자바 저장소이고 게임·함수형 이름이 섞여 있다 🔵 ([java-design-patterns](https://github.com/iluwatar/java-design-patterns/tree/4cabb204f240240bea319605a5ffa46ded728001)). Wikidata 는 CC0 주간 덤프라 고정 조건이 깔끔하다 🟡 ([Wikidata:Data access](https://www.wikidata.org/wiki/Wikidata:Data_access)). 그러나 "무엇이 설계 패턴 클래스의 인스턴스인가" 가 편집 관행에 달려 있어 경계가 흐리다(💭 60). SEBoK 용어집은 비상업(NC) 조건이다 🟡 ([SEBoK Copyright](https://sebokwiki.org/wiki/Bkcase_Wiki:Copyright)).

**iSAQB 와 닫힌 목록을 합쳐도 63개 중 30개만 덮는다** 🔵 재실측. 닫힌 목록이 iSAQB 밖에서 더하는 것은 polymorphism(GRASP), factory method · decorator(GoF) 셋이다. 남는 **33개**는 side effect · precondition · postcondition · single source of truth · inversion of control · inheritance · layered architecture · layering violation · circular dependency · dependency graph · call graph · call tree · caller · callee · data flow · deterministic · idempotent · granularity · testability · representation · code smell · technical debt · convention · bisect · production code · test code · prerequisite · edge · node · vertex · tree · stage · pipeline 이다. 사용자 결정("국제 표준 어휘 + 사용자 목록") 아래에서 이 33개는 SEVOCAB 에 있다고 확인되기 전까지 **사용자 목록으로만** 범위에 들어온다. 16개 목록으로 좁혀도 side effect · postcondition · circular dependency · call graph · technical debt · code smell 여섯은 어느 열린 목록에도 없다 🔵/🟡. 💭 70 — 이 여섯은 한국어 쪽에서도 가장 얇은 낱말들이다. circular dependency 는 한국어 근거를 어디서도 찾지 못했고, postcondition · call graph · technical debt · code smell 은 위키백과 표제(🟡)에만 기댄다. 그러니 공백은 번역 자원과 영어 쪽 열린 범위 목록 **양쪽에서 같은 자리에** 열려 있다. ## 결론

이번 조사가 바꾼 이해는 두 가지다. 첫째, 설계 어휘의 공백은 한국어 자원이 모자라서만 생기지 않는다. technical debt · code smell · call graph · postcondition 은 영어 쪽 열린 목록(iSAQB · 닫힌 목록 · Azure · java-design-patterns)에도, 한국어 용어집에도 함께 빠져 있고, SEVOCAB 수록 여부는 미확인이다 🔵/🟡. 💭 70 — 그래서 사용자 목록은 남는 낱말을 줍는 보조 수단이 아니라, 이 어휘 층의 범위를 정하는 **주된 수단**이 될 가능성이 크다. 그 비율은 SEVOCAB 을 한 번 조회하면 바로 정해진다. 둘째, 출처의 장점이 서로 엇갈려 분포한다. 라이선스가 깨끗하고 기계로 읽히는 곳(iSAQB · Azure 영어판)은 한국어가 없다. 한국어 범위가 가장 넓은 곳(위키백과)은 동일조건 의무를 진다. 허락이 가장 넓은 곳(ktword)은 일괄 경로가 없고, 이름이 가장 잘 정리된 곳(refactoring.guru)은 복제를 막는다. 💭 70 — 그러니 계획이 TTA 하나에만 쓰던 "손 조회 기록" 꼴이 설계 어휘에서는 예외가 아니라 기본 꼴이 된다. 행 스키마가 커밋 고정 행과 손 조회 행을 처음부터 같은 급으로 다뤄야 한다는 뜻이다.

실무적으로는, 사용자가 정한 "무게 = 범위·우선순위" 가 플랫폼 용어집을 빼느냐 두느냐는 논쟁을 풀어 준다. 위험의 실체는 플랫폼 종속이 아니라 동형이의다. 의미 표지 열(E6)만 있으면 쿠버네티스·MDN 의 행은 맨 아래 층에서 해를 끼치지 않는다 💭 75. 또 한국어 표기가 외래어 표기법 진영(`옵서버` · `싱글턴` · `리팩터링`)과 실무 진영(`옵저버` · `싱글톤` · `리팩토링`)으로 출처 계열을 따라 깔끔하게 갈리므로, "표기 진영" 열 하나가 고르지 않는 조회 자료에서 정보량이 가장 큰 열이 될 수 있다 💭 65.
